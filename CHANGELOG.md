## [2.3.0] - 2026-09-03

### Added
- **`scripts/rights_guard.py`** — детектор забытых прав/дыр в RLS без обращения к базе: объект
  расширения без единой строки прав ни в одной роли (ошибка — у ролей выключен флаг «права для
  новых объектов», право само не появится); безусловное право на заимствованный (типовой) объект в
  роли расширения (предупреждение — права складываются по ИЛИ, снимает типовое RLS-ограничение);
  запрос к таблице данных без `РАЗРЕШЕННЫЕ` без пометки-исключения (предупреждение — при RLS
  запрос падает целиком, а не фильтрует). `--strict` делает предупреждения тоже фатальными.
  `scripts/git-hooks/pre-commit` гоняет его на staged `.bsl`/`.mdo`/`Rights.rights` рядом с
  `bsl_guard`. PostToolUse-гейт харнесса Claude Code (`adapters/claude/settings.json`) — находка
  сразу в контексте после правки, инструкцию в промпте модель может пройти формально, харнесс-хук
  исполняет движок, не модель.
- **`core/skills/1c-metadata/references/edt-mcp-known-issues.md`** — известные ловушки EDT MCP
  (DitriX): модальное окно вместо «таймаута» при смене типа реквизита, форматы типа реквизита формы
  vs метаданного, обязательный `adopt_metadata_object` перед ссылочным типом на объект базовой
  конфигурации, ложный синтакс-фейл `write_module_source` на однострочных `Если…КонецЕсли`,
  метаданные откатываются мержами (диагностика по блобам, а не `git log`), коллизия id при автомерже
  `.form`, `export_configuration_to_xml` ломается на больших заимствованных формах.
- **`core/skills/1c-dev/references/platform-form-api.md`** — ловушки API управляемой формы,
  проверенные рантаймом: нет плоского обхода `Элементы` (только `Найти`/`ПодчиненныеЭлементы`),
  тайминг перепоказа команд командного интерфейса после `ПриСозданииНаСервере`, команда формы не
  перехватывается расширением (нужно перехватывать метод, который она вызывает), `Параметры` формы
  живут только в исходном серверном вызове создания, требования к заимствованной форме (пустая
  секция реквизитов, расположение `ListSettings.dcss`).
- **`onec_metadata/ops/attribute_add.py`, фикс** — образец реквизита-объекта брался по всему файлу
  (`//md:Attribute` / `//attributes`) и мог оказаться внутри табличной части — новый реквизит тихо
  падал туда же (загрузка проходит успешно, поле не находится запросом). Образец теперь строго с
  корневого уровня объекта; явный отказ с подсказкой на `child add --parent`, если образца на корне
  нет. Регрессия закрыта тестом и синтетической фикстурой.
- **MCP `bsl-ls-native`** (issue #6) — нативный MCP-режим `bsl-language-server` ≥1.0 (JDK 21+):
  `analyze_file`, `document_symbols`, `find_references`, `call_hierarchy`, `hover`, `definition`,
  `type_info`, `global_member_info`, `global_member_search`, `type_at_position` — passthrough без
  нового Python-кода, дополняет батч-диагностики `bsl-ls`. Решение и живая проверка (CLI-совместимость
  0.28.5→1.0.7, реальный JSON-RPC диалог, риски экспериментального MCP-режима у 1c-syntax) —
  `docs/design/2026-08-12-bsl-ls-mcp-mode.md`. `scripts/detect_tools.py`: `BSL_LS_VERSION` по
  умолчанию `1.0.7`, добавлена реальная проверка версии JDK (не только наличие `java`).
- **`1c-tester`, `unit-test-conventions.md`** — необязательные пункты чек-листа (не отдельный
  блокирующий этап): при сомнении в сигнатуре — `bsl-ls-native` (`hover`/`type_info`) вместо
  догадки; при правке общей функции — `find_references`/`call_hierarchy` на предмет регресса у
  других вызывающих.
- **`1c-estimation`, `estimation-by-analogy.md`** — раздел «Инструментальный сигнал размера — blast
  radius по коду»: объективный сигнал числа вызывающих мест (`find_references`/`call_hierarchy`)
  как вход для подбора аналога и оценки объёма регресса, не замена оценки по аналогии.

### Changed
- **`1c-estimation`, порог блокера смягчён** по итогам прямого сравнения с реальным результатом
  (round 1): тест «есть ли у разработчика безопасный, дёшево поправимый дефолт» — если да,
  неблокирующее с предложенным дефолтом; блокер — только пустой required-блок целиком, решение,
  влияющее на несколько будущих задач/контуров, или ошибка, ломающая фундамент проектирования.

### Added

  механизм — явный вопрос по объёму, не тихая находка; закрывает замечание тот, кто его выставил, а

  закрытых задачах вместо суммы придуманных атомов, гейт качества исторических данных о факт-часах,
  протокол проверки ЧТЗ тех-лидом по рамке `requirements` и формат списка замечаний

### Fixed
- `.claude/skills` пересобран из `core/skills` (`build.sh`) — расходился с ядром после добавления
  `1c-tester` (не был пересобран), `core/AGENTS.md`/`README.md`/`docs/TOOLS.md` не упоминали
  `1c-tester` в списке скиллов.
- Убраны случайные упоминания стороннего личного репозитория в generic-документации
  (`analysis-workflow.md`, `data-access-verification-runbook.md`, `designer_sync.py`) — публичный
  toolkit не должен ссылаться на чей-то конкретный процесс/инструмент.
- **`scripts/git-hooks/pre-commit`, реальный баг:** ранний `exit 0` в bsl-guard-секции (нет staged
  `.bsl`) обрывал ВЕСЬ хук до rights-guard — коммит нового объекта метаданных без единого `.bsl`
  (самый частый сценарий проверки object-without-rights) проходил вообще без проверки. Обе секции
  переведены на `if [ -n ... ]` вместо ранних `exit`. Воспроизведено и закрыто тестом на самом
  hook-скрипте, не только на `rights_guard.py` напрямую.
- **`scripts/git-hooks/pre-commit`, второй баг той же секции:** `git diff --name-only` без `-z` при
  `core.quotepath=true` (дефолт git) заворачивает кириллические имена — почти все объекты 1С — в
  кавычки с восьмеричным экранированием (`"src/...\320\257...mdo"`); строка кончается на `"`, а не
  на `o`, `grep -iE '\.mdo$'`/`\.bsl$` перестаёт матчить, файл тихо выпадает из проверки. Баг был и в
  исходном `bsl_guard`-блоке, маскировался нестандартным `core.quotepath=false` на машине автора.
  Пойман реальным падением CI (Ubuntu-раннер, дефолтный git). `-z` (NUL-разделитель) путь не
  квотирует независимо от `core.quotepath` — тест закрепляет сценарий явным `core.quotepath=true` в
  фикстуре, чтобы не зависеть от конфига машины разработчика.
- **`GEMINI.md`** тречился в git с mode `120000` (символьная ссылка), хотя содержимым была полная
  копия `AGENTS.md`, а не короткий путь-таргет — на Windows `build.sh` без реальной NTFS-привилегии
  на символьные ссылки записал в файл полный текст, git оставил старый mode. GitHub Actions падал на
  checkout: `unable to create symlink GEMINI.md: File name too long`. `build.sh` больше не пытается
  делать символьную ссылку для `GEMINI.md` вовсе — обычная копия, как у `AGENTS.md`/`CLAUDE.md`.
- **Обезличивание примеров:** докстринг `scripts/atlassian.py` и тесты использовали реальный ключ
  тикета Jira и реальные числовые ID страниц Confluence вместо синтетических примеров; несколько
  документов слоя `data-access` и их тесты называли конкретную версию ERP-конфигурации клиента вместо
  обобщённой формулировки — toolkit заявлен как org-agnostic.

## [2.1.1] - 2026-07-29

### Fixed
- **Пин `mcp<2` в runtime-серверах и Docker.** v2.1.0 запинил только CI; сами серверы (`mcp/onec_mcp.py`,
  `onec_data_mcp.py`, `onec_ops_mcp.py`, `bsl_ls_mcp.py` — inline `dependencies`) и образы (`server/Dockerfile*`)
  тянули `mcp` без верхней границы, поэтому при свежей установке `uv run` ставил mcp 2.0.0 и падал на импорте
  `mcp.server.fastmcp`. Теперь везде `mcp>=1.2,<2` / `mcp<2`. Проверено: `uv run mcp/onec_mcp.py` поднимается.
- **Парсер `.env` (`load_dotenv_defaults`) съедал inline-комментарии в значение.** Строка вида
  `KEY=  # пояснение` давала значением `"# пояснение"`, а не пустоту, и `KEY=` (пусто) перетирало дефолт пустой
  строкой. Из-за этого локальный `.env` со строкой `ONEC_DATA_DEBUG_PATH=  # по умолчанию /hs/aidbg` ронял слой
  данных: `#` обрезал URL по фрагменту до `/base` → HTTP 404. Теперь загрузчик (обе копии — `onec_ops_mcp`,
  `onec_data_mcp`) срезает inline-комментарий у некавыченных значений и НЕ выставляет пустые (пусто = взять
  дефолт). `#` внутри кавычек сохраняется. Снимало ~21 «падение» тестов `onec_data` на машинах с локальным `.env`.

## [2.0.1] - 2026-07-24

### Fixed
- **Центральный `docker compose` не поднимался без тест-ИБ.** Сервис `onec-data` в v2.0.0 стал обязательным
  (`ONEC_DATA_BASE_URL:?` + `proxy depends_on onec-data`), из-за чего `compose up` падал везде, где слой данных не
  провизинен (центр на хосте, Work PC). Теперь `onec-data` — **opt-in через compose-профиль** `data`: дефолтный
  `compose up` поднимает `onec-code`/`onec-ops`/`proxy` (как раньше), а слой данных включается явно
  `docker compose --profile data up -d` при заданных `ONEC_DATA_*`. `ONEC_DATA_BASE_URL` смягчён с `:?` на `:-`,
  зависимость `proxy → onec-data` убрана (иначе compose поднимал бы сервис вопреки профилю).
