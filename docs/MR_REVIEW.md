# Ревью merge request на 1С: первый проход, ворота в CI, вторая модель, метрики

Зачем. С ИИ в команде растут число и размер MR и нагрузка на ревью, а часть MR сливается без ревью. Эти средства снимают с человека механическую часть и оставляют ему смысл: поведение, архитектуру, риск. Числа из исследований (рост размера MR, времени ревью, нестабильности) сверяйте с первоисточниками перед публичным использованием.

## 1. Размер и правило декомпозиции
Размер MR для 1С считается не строками выгрузки, а числом затронутых объектов метаданных и ручными строками BSL (`scripts/mr_size.py`). Жёсткого лимита нет. Порог «требует обоснования» по умолчанию больше 15 объектов или больше 400 ручных строк BSL, настраивается `--max-objects` и `--max-bsl`. Выше порога в описании нужен абзац «Обоснование размера». Смешанный MR (поведение, рефакторинг и права вместе) разбивается. Чек-лист и приоритеты находок: `core/skills/1c-dev/references/review-checklist.md`.

## 2. Автоматический первый проход
`python scripts/mr_review.py --base origin/main --description mr.md [--tz постановка.md]` печатает короткий список P1 и P2: размер, части описания (что, зачем, как проверить, риск), `bsl_guard`, `rights_guard`, частые ключи BSL LS (если есть `BSL_JAR` и java). Код выхода 1 при P1. Находок нет не значит ошибок нет, для этого человек и ревью по чек-листу.

## 3. Ворота до человека в CI GitLab
Бесплатные детерминированные средства: `mr_review.py` (выше), BSL Language Server, SonarQube с плагином BSL, автотесты там, где они есть. Начинайте в информационном режиме (`allow_failure: true`), перед блокирующим режимом сверьте долю ложных срабатываний.

```yaml
mr-review-gate:
  stage: test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  variables:
    GIT_DEPTH: "0"
  script:
    - git fetch origin "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
    - printf '%s' "$CI_MERGE_REQUEST_DESCRIPTION" > mr.md
    - python "$ONEC_TOOLKIT_DIR/scripts/mr_review.py" --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME" --description mr.md
  allow_failure: true
```
Путь к набору (`ONEC_TOOLKIT_DIR`) задайте на раннере; машины без современных бинарников (старые Windows-раннеры) для этого джоба не подходят.

## 4. Вторая модель как проверяющий
`python scripts/mr_review.py --base origin/main --description mr.md --tz постановка.md --second-opinion` собирает запрос: дифф, постановка, чек-лист и описание вложениями, просьба искать дефекты по P1 и P2 и по каждому разделу чек-листа ответить, что именно проверено. Формулировка «ошибок нет?» снижает число найденного, поэтому её в запросе нет.

Корпоративный код 1С это закрытый класс данных. Допустимы только корпоративные средства: **M365 Copilot** и **Codex** (по вашему договору и настройкам обучения) и локальные модели. Бесплатные внешние модели и модели без корпоративного договора на нём не используются: переменная `AI_TOOLKIT_CORP=1` отключает звено «модель без обучения» в `second_opinion.py`. Бесплатные модели годятся для публичного обезличенного кода и тестовых примеров.

Подключение без личной настройки: онбординг набора сам проверяет Edge и Codex (`scripts/copilot_setup.py`, `scripts/codex_setup.py`), вход в M365 и `codex login` делает человек один раз. Статус: `python scripts/second_opinion.py status`.

## 5. Метрики для квартального разбора пропущенных дефектов
Что собираем автоматически:
- **Дефекты после релиза.** В Jira: баги, созданные после даты релиза, с полем «версия, где найден» (или меткой релиза). JQL-пример: `type = Bug AND created >= "<дата релиза>" AND fixVersion is not EMPTY`. Список выгружает `scripts/atlassian.py jira search "<JQL>" --json`.
- **Что принесло дефект.** `scripts/defect_trace.py --fix <коммит исправления>` находит по `git blame` коммиты, которые ввели исправленные строки, и ключи задач из их сообщений. Задача связывается с MR по ключу в названии ветки или MR.
- **Как MR прошёл ревью.** По GitLab API: число комментариев ревью, время до первого ревью, был ли слит без ревью, размер MR (`mr_size.py`).

Вопросы на разборе: какая задача и какой MR принесли дефект? Был ли MR слит без ревью или с формальным? Был ли он крупнее порога? Какой пункт чек-листа сработал бы? Что мог поймать автоматический проход, чего не поймал? Что поменять в чек-листе, воротах или описании MR? Считайте динамику по кварталам, а не оценку людей: сравниваются периоды и команды, не разработчики.

Ограничение. Трассировщик находит автора строки, а не причину. Рефакторинг и перенос кода дают шум, смотрите на повторяющиеся задачи и модули.

## Ревью по номеру MR из GitLab
```bash
GITLAB_HOST=gitlab.example.ru GITLAB_TOKEN=... python scripts/mr_review.py --mr 12 --project группа/проект
```
Читает описание, статус, размер, наличие CI и дифф MR через API (только чтение), показывает находки по описанию и CI и по умолчанию просит второе мнение другой модели (`--no-second-opinion` отключает). Токен берётся из `GITLAB_TOKEN` или `GITLAB_PERSONAL_ACCESS_TOKEN`, узел только явный (`--host` или `GITLAB_HOST`: имя узла и необязательный порт, без логина, пути и параметров), перенаправления запрещены, чтобы токен не ушёл на другой адрес. Ошибки сети и ответа печатаются коротко, без токена. Дифф с кодом корпоративного проекта уходит только корпоративным проверяющим (`AI_TOOLKIT_CORP=1`).
