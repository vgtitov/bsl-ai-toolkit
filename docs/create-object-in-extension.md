# onec_metadata: создать новый объект / копию объекта в расширении

Задача на доработку движка `onec_metadata` (bsl-ai-toolkit / claude-1c-toolkit).
Статус: **спецификация + уроки реальной доработки**, реализация — в бэклог
`onec_metadata/BACKLOG.md`.

## BLUF

Сейчас движок умеет только **добавление** дочерних элементов (`add_child`,
`attribute add`, `subsystem add-content`, `scd add-field` …). Создание **нового
объекта целиком** (или копии типового объекта с изменённой частью — напр. отчёта с
доработанной СКД) — **вне scope**, делается ручной правкой XML. Это повторяемая
операция с набором неочевидных ловушек (ниже). Нужна отдельная операция
`object add` / `object copy` / `object delete`.

Главные неочевидные факты, найденные на платформе **8.3.25.1445** (эмпирически,
через реальную загрузку в тест-базу):

1. `ObjectBelonging` нового объекта = **`Native`** (не `Added`, не `Own`).
2. Новый объект ОБЯЗАТЕЛЬНО регистрировать в `<ChildObjects>` файла
   `Configuration.xml` расширения.
3. Дата/число-поля в кросс-таблице СКД требуют `<totalField>`, иначе не выводятся.

## 1. Уроки реальной доработки (2026-08, платформа 8.3.25.1445)

### 1.1 `ObjectBelonging` нового объекта = `Native`

- Принятое значение для нового («собственного») объекта расширения — **`Native`**.
  Значения `Added` и `Own` платформа отвергает с ошибкой
  «Неверное значение перечисления - …» (проверено `LoadConfigFromFiles`).
- При **обратной выгрузке** платформа пишет Native-объект **без** `ObjectBelonging`
  (это значение по умолчанию, оно не сериализуется).
- Для заимствованного объекта значение по-прежнему `Adopted`.
- **Расхождение источников (важно для кроссплатформенности):** библиотека
  `mdclasses` (1c-syntax, master 2019–2026) объявляет
  `ADOPTED("Adopted")`, `OWN("Own")`, `UNKNOWN("unknown")` — т.е. НЕ знает
  `Native`. Платформа же пишет/принимает `Native`. Вывод: на 8.3.x опираться на
  поведение платформы (`Native`), а не на константу `OWN` из mdclasses; перед
  поддержкой 8.3.27+/8.5 проверить значение заново (см. §3).

### 1.2 Регистрация в манифесте `Configuration.xml`

Новый объект обязательно добавляется в `<ChildObjects>` корневого
`Configuration.xml` расширения (`<Report>Имя</Report>`, `<Subsystem>Имя</Subsystem>`
и т.п.). Иначе `LoadConfigFromFiles` падает: `Файл объекта не существует - …/<Тип>/<Имя>.xml`.

Вложенные объекты (напр. подсистема внутри подсистемы) в корневом `ChildObjects`
**не** перечисляются — они указываются в `ChildObjects` своего родителя (§1.6).

### 1.3 Удаление заимствованного объекта = «ан-адопт»

Удалить файл(ы) объекта из исходников расширения + `LoadConfigFromFiles` →
объект исчезает из расширения, типовая версия возвращается. Подтверждается дампом:
объект отсутствует в `<Тип>/`.

### 1.4 Копия типового объекта — копировать ВСЁ дерево

«Копия типового отчёта» ≠ копия только изменённой СКД. Нужно переносить полное
дерево: `Ext/`-модули (`ObjectModule.bsl`, `ManagerModule.bsl`), `Help`, `Templates/`,
и свойства `MainDataCompositionSchema`, `DefaultForm`, `Synonym`. Иначе новый
объект теряет серверную логику (у отчёта — `ПриКомпоновкеРезультата`, отборы,
картинки и т.п.).

При этом ссылки внутри объекта на себя пересчитать на новое имя (напр.
`MainDataCompositionSchema = Report.НовыйИмя.Template.…`), а uuid сгенерировать
заново (§2).

### 1.5 `<ChildObjects/>` (пустой) = наследовать детей из типовой

У заимствованного (`Adopted`) объекта пустой `<ChildObjects/>` означает
«наследовать всех дочерних из типовой конфигурации», а **не** «нет детей».
Подтверждено: Adopted-каталоги с `<ChildObjects/>` наследуют реквизиты/ТЧ.

### 1.6 Вложенные подсистемы

Подсистема, вложенная в другую (напр. `CRMИМаркетинг → ЦеныИСкидки`), для
заимствования требует:

- заимствовать **родителя** (минимально: `Adopted` + `Name` + пустой
  `<ChildObjects/>`), разместив его по пути `<Subsystems>/<Родитель>.xml`;
- вложенную разместить по пути `<Subsystems>/<Родитель>/Subsystems/<Имя>.xml`;
- в `ChildObjects` родителя перечислить заимствованную вложенную
  (`<Subsystem>Имя</Subsystem>`) — это дельта, остальные дети наследуются;
- в корневом `Configuration.xml` — только топ-уровневого родителя.

Ошибка при неверном размещении: `UpdateDBCfg … Не найден объект Подсистема.<Имя>`.

### 1.7 `ExtendedConfigurationObject` (UUID типового объекта)

При `KeepMappingToExtendedConfigurationObjectsByIDs=true` у расширения ссылки на
объекты типовой конфигурации маппятся **по UUID**. В дескрипторе заимствованного
объекта это поле `<ExtendedConfigurationObject>UUID</ExtendedConfigurationObject>`
(в `Properties`, после `Comment`). Встречается у StyleItem/DefinedType/подсистем;
у каталогов/документов/отчётов маппинг по имени работает и без него. Правило:
если маппинг по имени не срабатывает («Не найден объект …») — добавить UUID
типового объекта.

### 1.8 `totalField` для дат/чисел в кросс-таблице СКД

Поле, выводимое в кросс-таблице СКД (в детальных записях/группировках), обязано
иметь `<totalField>` с выражением агрегации (напр. `Максимум(Поле)`). Без него
поле есть в схеме, но **не попадает в вывод** (типично для дат/чисел; у строки
также нужен — см. существующий `totalField` для строкового поля-номера).
Эмпирически: после добавления `totalField=Максимум` дата-колонки появились в
выводе. См. `onec_metadata/BACKLOG.md` (урок «Поле не может быть использовано в
группировке»).

### 1.9 Маркеры, подставляемые `ObjectModule.bsl` в `ПриКомпоновкеРезультата`

При правке запроса СКД отчёта сохранять маркеры-плейсхолдеры, которые заменяет
`ObjectModule.bsl` в рантайме (`&ТекстЗапросаКоэффициентУпаковки`,
`&ПодстановкаТоварногоОграничения`, `&НаборыВыводятся` и т.п.). Их потеря = рантайм
падение/неверная компоновка, при том что загрузка пройдёт.

### 1.10 Роль (Role) в расширении — права на собственный объект

Собственный объект расширения (отчёт/обработка/роль) **без роли расширения не
виден обычным пользователям**: права задаются ТОЛЬКО ролями расширения, а основные
роли новый объект не знают (проверено grep'ом по 946 ролям основной конфигурации —
новый отчёт не упомянут ни в одной, тогда как типовой донор — в 9+). Решение —
добавить Роль в расширение:

- `Roles/<Имя>.xml` — как Role.xml основной конфигурации, но **БЕЗ**
  `InternalInfo`/`xr:GeneratedType` (роль не порождает типов) и **БЕЗ**
  `ObjectBelonging` (новый объект = Native, не сериализуется). Только
  `<Role uuid>` + `<Properties>` (Name/Synonym/Comment).
- `Roles/<Имя>/Ext/Rights.xml` — **другой namespace** (`http://v8.1c.ru/8.2/roles`,
  корень `<Rights xsi:type="Rights" version="2.18">`), не `8.3/MDClasses`. Право на
  собственный объект расширения — **по имени** (`<name>Report.<Имя></name>`), не по
  UUID. Для видимости отчёта достаточно `Use` + `View` (регистры отчёт читает
  типовые — права на них уже есть у ролей, видящих типовой донор).
- регистрация `<Role>Имя</Role>` в `<ChildObjects>` Configuration.xml (каноничное
  место — после CommonForm, перед Catalog; платформа при UpdateDBCfg переставит сама).
- **НАЗНАЧЕНИЕ роли — это ДАННЫЕ ИБ, а не конфигурация**:
  `ПользователиИнформационнойБазы.НайтиПоИмени(<Логин>).Роли.Добавить(Метаданные.Роли.Найти(<Имя>))`
  + `Записать()`. Делается смоук-сценарием под полными правами. Без назначения роль
  бесполезна. `Метаданные.Роли.Содержит(...)` ждёт ОБЪЕКТ метаданных, а не строку —
  искать по имени через `Метаданные.Роли.Найти(<Строка>)`.

### 1.11 Ручная правка дампа: BOM + CRLF

Файлы дампа Конфигуратора — UTF-8 **с BOM** и **CRLF**. Ручная правка через Python
`open(path).read()/write()` НЕЯВНО портит CRLF→LF (universal newlines) и теряет BOM —
файл становится «весь diff». Читать/писать с `encoding="utf-8-sig", newline=""`
и явно держать `\r\n`. Имена файлов на Windows платформа отдаёт в NFD
(«й» = и + U+0306), macOS/git — NFC; при сравнении нормализовать (`unicodedata.normalize`).

## 2. Механика создания нового объекта (что должна делать операция)

Для нового объекта (`ObjectBelonging=Native`) в расширении:

- **uuid объекта** — свежий `uuid4`.
- **`InternalInfo`/`xr:GeneratedType`** — регенерировать `TypeId`/`ValueId` (для
  типогенерирующих объектов: Report → `ReportObject.<Имя>`/`ReportManager.<Имя>`
  и т.п.). Для простых объектов (подсистема) `InternalInfo` отсутствует.
- **`ObjectBelonging`** = `Native` (или вовсе опустить — платформа считает Native
  по умолчанию и не сериализует его).
- **регистрация** в `Configuration.xml` `<ChildObjects>` (или в родителе для
  вложенных).
- **свойства-ссылки на себя** пересчитать на новое имя.

Операции-кандидаты (по аналогии с существующими `add_child`/`subsystem add-content`):

- `object copy --donor <Тип.Имя> --name <Новый> [--replace-template <…>]` —
  полная копия типового объекта + подмена части (СКД/макет/модуль).
- `object delete --ref <Тип.Имя>` — ан-адопт (удалить из исходников + из манифеста).
- `subsystem add-content` — доработать для **вложенных** подсистем (родитель +
  путь + ChildObjects дельта).

## 3. Версионные различия формата дампа

Формат XML-дампа помечен в шапке `<MetaDataObject … version="X.Y">`.

- **8.3.25** → `version="2.18"` (наблюдение на рабочей конфигурации).
- **8.5** → `version="2.21"`: в шапку добавлено пространство палитры
  `xmlns:pal="http://v8.1c.ru/8.1/data/ui/colors/palette"` (вставляется по
  алфавиту: после `lf`, перед `style`). В `Rights.xml` палитра не идёт.
  Источник: `cc-1c-skills/role-compile.py` (`format_rank(version) >= 221`).
- Сравнение версий — **только числовым рангом** (`"2.20"→220, "2.9"→209`):
  строковое сравнение неверно (`"2.9" > "2.17"`).
- **8.3.27** — публичной документации по изменению `ObjectBelonging`/формата не
  найдено (поиск пуст). **Требование для переноса:** эмпирически проверить на
  8.3.27+ значение `ObjectBelonging` для нового объекта (Native vs Own) и версию
  формата дампа — и только потом фиксировать поддержку.

Инвариант для будущей реализации: версию формата определять по
`Configuration.xml` (или корню самого объекта для внешних отчётов/обработок), а не
хардкодить `2.18`.

## 4. DoD (приёмка операции)

- TDD: сначала падающий тест (обезличенная фикстура реальной структуры), потом код.
- Оба формата (Конфигуратор `*.xml` + EDT `*.mdo`), где применимо.
- byte-perfect минимальный дифф.
- Применение только в **тест-базу** + round-trip: повторная выгрузка даёт дифф
  ровно целевых файлов (учесть, что платформа канонизирует: Native без
  `ObjectBelonging`, `DefaultForm` резолвится в UUID при
  `KeepMappingToExtendedConfigurationObjectsByIDs=true`).
- Adversarial-ревью перед merge.
