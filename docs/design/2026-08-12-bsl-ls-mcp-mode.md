# BSL LS как MCP-сервер — решение и проверка (issue #6)

**Решение:** внедрить. Два инструмента вместо одного, оба поверх того же jar `bsl-language-server`:
`bsl-ls` (батч-диагностики, как раньше) + новый `bsl-ls-native` (нативный MCP-режим ≥1.0 — навигация
и типы). Обезличено, org-agnostic.

## Почему сейчас, а не когда issue завели (29.07)

Issue #6 указывал на релиз 1.0 и ссылку на McpMode/capabilities. Пин toolkit на момент issue —
`bsl-language-server 0.28.5` (до нового движка типов, без MCP вообще). Решение требовало не верить
описанию из документации, а прогнать jar живьём (правило toolkit «спроси инструмент, не угадывай» —
применено к себе).

## Что проверено живьём (не по документации)

Окружение: Windows, `java` в PATH — Zulu **17** (не годится, см. ниже), Zulu **21.0.8** развёрнута
отдельно для проверки.

1. **`bsl-language-server 1.0.7` требует JDK 21+.** Запуск под JDK 17 →
   `UnsupportedClassVersionError: class file version 65.0 … recognizes up to 61.0` (65 = Java 21,
   61 = Java 17). Подтверждено и по `build.gradle.kts` апстрима: `sourceCompatibility = VERSION_21`.
   `mcp-bsl-context` (`bsl-platform`, другой проект) в JDK 21 не нуждается — на 17+ как раньше.
2. **CLI `analyze` не менялся структурно.** Флаги `-s/--srcDir`, `-o/--outputDir`, `-r/--reporter`,
   `-q/--silent` — те же, что использует `mcp/bsl_ls_mcp.py`. Прогон 0.28.5→1.0.7 на тестовом файле
   с анти-паттерном (запрос в цикле) дал ту же структуру JSON-отчёта (`fileinfos[].diagnostics[]`
   с `severity`/`code`/`message`/`range`) — **мост `bsl_ls_mcp.py` не требует правок кода**, только
   версия jar и JDK.
3. **Нативный MCP-режим (`java -jar bsl-ls.jar mcp --protocol=stdio`) — реальный, работающий MCP
   stdio-сервер.** Ручной JSON-RPC клиент (`initialize` → ответ на серверный `roots/list` →
   `tools/list` → `tools/call`) подтвердил:
   - `tools/list` вернул **10** инструментов (не 11, как в одной из версий доки): `analyze_file`,
     `document_symbols`, `find_references`, `call_hierarchy`, `hover`, `definition`, `type_info`,
     `global_member_info`, `global_member_search`, `type_at_position` — с полными JSON Schema.
   - `analyze_file`, `document_symbols`, `global_member_info("Сообщить")`, `type_info("Массив")` —
     вызваны и вернули содержательные, корректные ответы (сигнатуры, RU/EN, since-версии, примеры).
   - `hover`/`document_symbols` **требуют, чтобы файл входил в заявленный клиентом workspace root**
     (сервер сам шлёт `roots/list` клиенту при `initialize` — это часть протокола MCP, не баг). Для
     одиночных вызовов без роли IDE (`analyze_file`, `global_member_info`, `type_info`) роль воркспейса
     не критична (для `global_member_info`/`type_info`/`global_member_search` `root` — обязательный
     параметр схемы, но подходит любой заявленный root).
   - Побочный эффект архитектуры: пути идут через JSON, не через argv процесса — **не воспроизводится
     баг с кириллицей в пути на Windows**, из-за которого `bsl_ls_mcp.py` несёт `_ascii_safe()`.

## Архитектура: два MCP-сервера, не один

`bsl-ls` (обёртка, `mcp/bsl_ls_mcp.py`) и `bsl-ls-native` (голый `java -jar … mcp`, без Python-кода)
решают разные задачи — не дублируют друг друга:

| | `bsl-ls` (обёртка) | `bsl-ls-native` (родной MCP) |
|---|---|---|
| Область вызова | каталог или файл, батч | один файл за вызов |
| Диагностика | да, со сводкой по severity + фильтром + явным «0 файлов = не проверено» | да (`analyze_file`), без сводки/фильтра |
| Навигация/типы | нет | `definition`/`find_references`/`call_hierarchy`/`hover`/`type_at_position` |
| Справка платформы | нет | `type_info`/`global_member_info`/`global_member_search` (RU/EN, since/deprecated, примеры) |
| Windows-кириллица в пути | требует `_ascii_safe()` (аргумент процесса) | не актуально (путь в JSON) |
| Зависимость | тот же jar + `uv`/`mcp<2>` (Python) | тот же jar, без Python-слоя |

Решение — **держать оба**, не сливать и не выбирать один: `bsl-ls` — гейт после правки (используется
в pre-commit/CI-подобных сценариях, где нужен явный вердикт по каталогу), `bsl-ls-native` — код-интеллект
для агента при чтении/навигации (замена части ручного grep на семантический поиск). Переименование
существующего `bsl-ls` не делалось — ключ мог быть уже прописан в чьём-то `.env`/оснастке.

## Риски и открытые вопросы (честно, не скрыто)

- **MCP-режим у 1c-syntax официально экспериментальный** (Spring AI 2.0 на момент их же документации
  — "API и поведение могут меняться"). Не обещаем стабильность схемы между минорными релизами
  bsl-language-server — прикладываем `BSL_LS_VERSION` явно, как и раньше.
- **Требование JDK 21+ — реальный порог входа.** Не у всех участников команды может быть JDK 21;
  `detect_tools.py` теперь явно ЭТО проверяет (не только «java есть») и подсказывает путь (обновить
  JDK или закрепить `BSL_LS_VERSION=0.28.5`, если 21 недоступна).
- **`root` в `global_member_info`/`type_info`/`global_member_search` — обязателен по схеме.** Указано
  как «URI одного из заявленных клиентом roots». Для Claude Code (заявляет workspace root
  автоматически) это прозрачно; для агентов без поддержки `roots` в MCP-клиенте — не проверено,
  пометка **[проверить]** на будущее, если появится жалоба под другим агентом.
- **Частичное пересечение с `bsl-platform` (`mcp-bsl-context`, сторонний проект `alkoleft`).**
  `global_member_info`/`type_info` закрывают часть той же нужды (справка платформы) из того же jar,
  что уже даёт диагностики — но это НЕ повод объявить `bsl-platform` избыточным без отдельного
  прямого сравнения полноты базы (не проводилось в рамках этой проверки). Оставлено как открытый
  вопрос на будущее, оба инструмента продолжают жить параллельно.

## Смежный вывод: пробел в тестах и оценке (не в доступе к данным)

Отдельный вопрос — где новые семантические возможности (`type_info`/`hover`/`find_references`/
`call_hierarchy`) должны отразиться в СМЕЖНЫХ скиллах toolkit. Проверены три:

- **`1c-tester` (тесты).** Реальный пробел: `unit-test-conventions.md` не упоминал ни одного способа
  проверить сигнатуру функции инструментом перед тем, как писать Arrange — только чтение модуля
  глазами. Добавлено: сверка сигнатуры через `hover`/`type_info`/`type_at_position` перед тестом;
  оценка «зоны поражения» правки через `find_references`/`call_hierarchy` как сигнал ширины регресса
  (не арифметика — сигнал объёма покрытия). См. раздел «Перед тестом — сигнатура точно, не по памяти».
- **`1c-estimation` (оценка).** Реальный пробел: классификация размера (S/M/L/XL) — целиком на
  субъективном чтении описания задачи, без объективного сигнала о фактическом radius влияния правки
  в существующем коде. Добавлено: раздел «Инструментальный сигнал размера — blast radius по коду» —
  явно ДОПОЛНЯЕТ аналогию (не заменяет, не превращается в «сумма атомов по числу вызовов» — против
  этого прямо предупреждает основной метод скилла).
- **`onec-data` / работа с информационной базой (данные).** Проверено и **пробела не найдено** —
  слой уже спроектирован, реализован (10 инструментов `onec_data_mcp.py`, расширение `ai_debug`),
  покрыт тестами (17 зелёных на момент `data-access-architecture.md`) и проверен round-trip на живой
  базе 23.07.2026. Ощущение пробела здесь не подтвердилось — не стал придумывать доработку туда,
  где её объективно не требуется.
