# Issue и PR: единый порядок

Для тех, кто пишет в репозиторий, и для агентов, которые его ведут. Порядок ревью самого PR (замечания `блокер:` и `желательно:`, кто вливает) описан в [MR_REVIEW.md](MR_REVIEW.md) и [mr-review-agent.md](../core/skills/1c-dev/references/mr-review-agent.md).

## Сроки ответа
Рабочие дни, понедельник–пятница, без учёта праздников.

| Что пришло | Первый ответ автору | Что значит ответ |
|---|---|---|
| Новый issue | до 2 рабочих дней | принято, нужны данные (`needs-info`), не берём (`wontfix` с причиной) |
| Чужой PR | до 3 рабочих дней | ревью, вопрос или причина, почему не берём |

Ответом считается комментарий или ревью владельца, участника или соавтора репозитория. Молчание дольше срока считается нарушением, а не отсутствием новостей. Просроченное показывает `python scripts/review_inbox.py --issues`.

## Метки
Набор небольшой. Новые метки заводим, только если их некуда вписать.

| Метка | Когда |
|---|---|
| `bug`, `enhancement`, `documentation`, `question` | тип |
| `needs-info` | ждём данные от автора (воспроизведение, версия) |
| `accepted` | берём в работу, понятно что делать |
| `roadmap` | публичная карточка плана развития |
| `wontfix`, `duplicate`, `invalid` | закрыто с причиной в комментарии |
| `found-on:release`, `found-on:main`, `regression:unreleased` | где найден дефект: в выпущенной версии, в main, внесён после последнего тега |
| `wait:external` | ждём внешнее (платформа, плагин, ответ автора) |
| `area:metadata`, `area:mcp`, `area:onboard`, `area:skills`, `area:ci` | кластер |
| `windows`, `macos`, `linux` | где проявляется |
| `good first issue`, `help wanted` | для новых участников |

Milestone: версия, в которую задача должна войти (`v2.8`). Дат у milestone нет: даты создают обязательства, а релиз без готового не выпускается. Задача без milestone, но с `roadmap` значит «планируем, версия не назначена».

## Жизненный цикл issue
1. Появился. Ответ в срок: принято, `needs-info` или `wontfix` с причиной.
2. `accepted` и milestone, когда понятно что делать.
3. Дефект воспроизводится тестом: сначала падающий тест, потом исправление. Исправление отдельным PR, в описании `Fixes #N` (issue закроется при влитии).
4. После выпуска в issue один комментарий «выпущено в vX.Y.Z» со ссылкой на релиз. Без этого автор не узнает, что дошло до релиза.
5. Не воспроизводится или автор молчит 14 дней после `needs-info`: закрываем с причиной и просьбой открыть заново.

## Связь с CHANGELOG и релизами
- Каждая запись `CHANGELOG.md` из issue или PR кончается ссылкой `(#N)`.
- В заметках релиза перечислены влитые PR (`Fixes #N` связывает их с issue) и одной строкой итог: «Закрыто в версии: X issue, Y PR». Числа берутся из milestone версии: `gh api repos/<owner>/<repo>/milestones --jq '.[] | select(.title=="vX.Y") | "\(.closed_issues) \(.open_issues)"'`.
- Прогресс по плану виден на странице milestone и по фильтру `label:roadmap`.

## Что нельзя в публичных issue, PR и комментариях
Жёсткая граница. В публичное место не идут:
- внутренние темы организации, внутренние системы, базы, процессы, названия проектов и команд;
- анализ других систем, сравнения с конкурентами и их продуктами, ссылки «как у такого-то»;
- чувствительные и болевые темы: слабые места, уязвимости (для них [Security Advisories](../SECURITY.md)), оценки людей;
- имена организаций и людей, кроме автора обсуждения;
- оценки трудозатрат, приоритеты, даты релизов как обещания;
- логи, пути и примеры из рабочих баз (только обезличенные фикстуры).

Публичная карточка пишется с точки зрения пользы людям: что планируем, зачем, статус. Внутреннее обоснование, анализ и идеи из чужих проектов живут вне репозитория в закрытых заметках, связь по номеру публичной карточки.

Проверка перед публикацией любого текста наружу:
```bash
python scripts/public_check.py черновик.md --stoplist <путь вне репозитория>
```
Скрипт находит почту, телефоны, IP, внутренние хосты, ключи, личные пути и слова из приватного стоп-листа (его храните вне репозитория, путь в `PUBLIC_STOPLIST`). Тему, анализ и сравнения он не видит: пройдите чек-лист, который печатает скрипт. Код выхода 1 значит «не публиковать, пока не исправлено». Без стоп-листа скрипт завершается с кодом 2 (имена не проверены); `--allow-no-stoplist` снимает отказ, но тогда имена организаций и людей читайте глазами.

## Чужой PR
Срок ответа 3 рабочих дня. Агент читает дифф, запускает тесты (в изолированной среде) и проверку другой моделью, готовит ревью по правилам [MR_REVIEW.md](MR_REVIEW.md) (`блокер:`/`желательно:`) и показывает владельцу репозитория. Публикует комментарии и вливает только по явному слову владельца. Автору нужно ответить даже тогда, когда PR не берём: причина и что можно изменить.

Код чужого PR не запускается на машине владельца без его решения: сначала чтение диффа, запуск в изолированной среде или в CI.

## Свои PR
Изменения агента и участников идут веткой и PR. Вливает владелец репозитория, не автор изменения; блокеры закрывает ревьюер. Сам владелец может пушить в `main` (релизный коммит, срочная правка): защита ветки для него это разрешает, для остальных нет. Описание по шаблону, `Fixes #N`, запись в `CHANGELOG.md`.

## Что ведёт система сама
Задачи развития, доработки и исправления, которые система ставит себе, заводятся публичными issue в нейтральной формулировке и ведутся до закрытия: метка, milestone, ссылка на PR и релиз. Триггерные темы публично не заводятся, у них закрытая заметка. Создание, комментарии, закрытие и слияние на GitHub агент делает только по явному слову владельца репозитория; без него готовит черновик.
