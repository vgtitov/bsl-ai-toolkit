# Проверка L2 (OData) / L3 (ai_debug) — воспроизводимый путь на новой машине

> Единый рабочий путь, без «на выбор». Если ниже сказано «лучше X, но не настроено — делай Y» —
> Y обязателен сейчас, X появится отдельным пунктом, когда будет настроен (публикация на
> веб-сервере командой/админом). Все команды проверены живьём 29–30.07.2026.

## 0. Предварительные условия

- Платформа 1С установлена, версия и путь известны (`ONEC_1CV8_BIN`).
- В `.env` репозитория (`claude-1c-toolkit/.env`, не в `operkontur-work/.env` — скрипты читают
  `.env` из CWD и корня СВОЕГО репозитория): `ONEC_IB_USER`, `ONEC_IB_PASS_<КОНТУР>`.
  ⚠ Не дублировать `ONEC_IB_USER=` пустой строкой-заготовкой выше реальной — загрузчик `.env`
  берёт ПЕРВОЕ вхождение ключа, вторая строка молча игнорируется.
- `extensions/ai_debug/src` уже в репозитории (расширение написано, версионируется как код).
- Для серверной базы через SSH — алиас в `~/.ssh/config` (см. `onec-work-mechanisms.md`),
  переменная `ONEC_REMOTE_WORKDIR` на писабельный каталог под учёткой на сервере.

## 1. Какой у вас случай — определяет ВСЁ дальнейшее

| У вас есть... | Сценарий |
|---|---|
| Только файловая копия базы локально | **A. Автономный сервер** |
| Только серверная (клиент-серверная) база, доступ по SSH к терминалу рядом с кластером | **B. SSH + деплой на серверную базу** |
| База уже опубликована на веб-сервере админом | **C. Прямая работа с публикацией** (лучший вариант — не тратит время на A/B; если публикации ещё нет, попросите её у админа/DevOps, а пока нет — работайте по A или B) |

Если доступны оба (A и B) — начинайте с A: файловая копия ваша личная, не расходует
корпоративные ресурсы и ничего не меняет на серверах команды.

## Сценарий A — автономный сервер на файловой копии

### A.1 Поднять сервер

```
cd claude-1c-toolkit
export PYTHONUTF8=1
export ONEC_1CV8_BIN='C:\Program Files\1cv8\<версия>\bin\1cv8.exe'
python scripts/onec_verify.py serve --base "<путь к файловой базе>" --port 8315 \
  --name <короткое_имя> --service aidbg_API:aidbg
```

`--service aidbg_API:aidbg` **обязателен**, если в базе уже есть загруженное расширение
`ai_debug` (или другое с HTTP-сервисом) — без поимённой публикации HTTP-сервисы расширений
не публикуются сами (даже с `publish-extensions-by-default: true`), эндпоинт отдаёт 503.
Без него — просто `serve --base ... --port 8315` (для голого OData этого достаточно).

Проверка: `curl -s -o /dev/null -w "%{http_code}" http://localhost:8315/` → `200`.

### A.2 Задеплоить расширение `ai_debug` (если его ещё нет в базе)

Локальный DESIGNER на этой машине — **GUI-приложение**; голый `subprocess.run`/`Process.Start`
без обёртки не даёт ему открыться и тот падает с `exit code 1` и ПУСТЫМ логом/выводом — не путать
с ошибкой авторизации или занятой базой (у тех есть текст в логе). Три вещи чинят это разом:

1. Запускать через `cmd /c start /wait ""` — даёт процессу нормальный оконный хендл.
2. Путь к базе — **8.3-короткое ASCII-имя**, если в пути есть кириллица (иначе тоже
   безмолвный отказ). Получить: `(New-Object -ComObject Scripting.FileSystemObject).GetFolder("<путь>").ShortPath`.
3. `LoadConfigFromFiles` и `UpdateDBCfg` — **два отдельных вызова**, не один командой.
4. Перед запуском убедиться, что база не занята: `Get-Process -Name 1cv8,1cv8c` — если что-то
   висит (включая ваш же интерактивный Конфигуратор на этой базе), закрыть/`Stop-Process`.

```powershell
$user = "<ONEC_IB_USER>"; $pass = "<ONEC_IB_PASS>"
$shortPath = (New-Object -ComObject Scripting.FileSystemObject).GetFolder("<путь к базе>").ShortPath
$exe = "<ONEC_1CV8_BIN>"
$log1 = "$env:TEMP\ext_load_step1.log"; $log2 = "$env:TEMP\ext_load_step2.log"

cmd /c ('start /wait "" "' + $exe + '" DESIGNER /F "' + $shortPath + '" /N"' + $user + '" /P"' + $pass + `
  '" /DisableSplash /DisableStartupDialogs /DisableStartupMessages /LoadConfigFromFiles ' + `
  '"C:\dev\tvg\rp\claude-1c-toolkit\extensions\ai_debug\src" -Extension ai_debug /Out "' + $log1 + '"')
Get-Content $log1 -Encoding UTF8 -Raw   # пусто = успех

cmd /c ('start /wait "" "' + $exe + '" DESIGNER /F "' + $shortPath + '" /N"' + $user + '" /P"' + $pass + `
  '" /DisableSplash /DisableStartupDialogs /DisableStartupMessages /UpdateDBCfg -Extension ai_debug /Out "' + $log2 + '"')
Get-Content $log2 -Encoding UTF8 -Raw   # пусто = успех
```

Пустой лог на обоих шагах = успех (та же конвенция, что у `dumpload.py`: непустой лог или
`Ошибк*`/«недостаточно прав» — провал).

После деплоя — перезапустить сервер (A.1), чтобы новый HTTP-сервис подхватился.

## Сценарий B — серверная база через SSH (нет локального файла)

Плацдарм — терминал рядом с кластером (см. `~/.ssh/config`, алиас, например `vc-d-rds-01`).
Локальный DESIGNER здесь не нужен вовсе — тем же путём идут point dump/load и smoke.

### B.1 Задеплоить расширение — одной командой, без ad hoc скриптов

```
python scripts/designer_sync.py deploy-extension \
  --base 'сервер\база' --host <алиас-ssh> --ext ai_debug \
  --src extensions/ai_debug/src --contour <КЛЮЧ>
```
Заливает весь `src/` на сервер, делает `LoadConfigFromFiles` + `UpdateDBCfg` за один вызов.
Идемпотентно — можно гонять повторно при правках расширения.

### B.2 Публикации на этой базе, скорее всего, ещё нет

Тогда HTTP-контракт (`/hs/aidbg/*`, OData) недоступен вообще — это не баг, а отсутствие
публикации (см. §3 «Признаки по коду ответа»). Рабочий канал без публикации — ступень 2
лестницы тестирования (`docs/testing-ladder.md`): смоук-сценарий вызывает простые функции
расширения (без HTTP-обёртки, `aidbg_Настройки.*`) напрямую:

```
python scripts/onec_verify.py smoke --base 'сервер\база' --host <алиас-ssh> --contour <КЛЮЧ> \
  --scenario <файл.bsl>
```
где `<файл.bsl>` вызывает `aidbg_Настройки.ПривилегированныйРежимРазрешен()` и т.п.
⚠ Функции `aidbg_Сервер.Обработать*` принимают объект `HTTPСервисЗапрос` — его нельзя
сконструировать из BSL-сценария, этим путём HTTP-контракт не проверить в принципе.

**Лучше, если доступно:** попросить публикацию у админа веб-сервера (см. §4) — тогда тот же
`ai_debug`, задеплоенный этой командой, сразу проверяется полным HTTP-контрактом без смоука.

## Сценарий C — база уже опубликована (лучший случай)

Ничего из A/B не нужно — публикация уже даёт HTTP-эндпоинт. Сразу к §3 (проверка) с
адресом публикации вместо `localhost:8315`. Не тратит лицензию клиента на каждый вызов,
не нужен отдельный процесс на машине разработчика — если публикация доступна, это и есть
эффективный путь, к которому стоит перейти, как только админ её сделает.

## 2. Роль `Удаленный доступ (OData)` — как выдать

БСП-конфигурации (ERP, УТ, КА) не имеют отдельного флажка в карточке пользователя — роль
выдаётся через профиль группы доступа. Проверить, есть ли уже подходящий профиль:
Администрирование → Настройки пользователей и прав → Профили групп доступа → найти профиль
с ролью `Удаленный доступ (OData)` (поиск по слову «OData» внутри списка ролей профиля).

Если такого профиля нет или подходящий выдаёт слишком много лишних прав — создать узкий:
1. Профили групп доступа → Create → название, роль (поиск «OData», отметить галкой) → Записать и закрыть.
2. У этого профиля — вкладка «Группы доступа» → Create group → название → добавить
   нужного пользователя через «Подобрать» → Записать и закрыть.
3. Пользователю нужно **выйти и зайти заново** (Sign out / Log in) — права новой сессии
   подхватываются при входе, не в уже открытой сессии.

## 3. Проверка — одни и те же команды для A/B/C (меняется только адрес)

### 3.1 Три обязательные поправки на кодировку (Windows curl.exe из Git Bash)

Без них ЛЮБОЙ из трёх сценариев даст ложный 401/404 с кириллицей внутри:

```bash
# 1. Basic-auth: НЕ curl -u "логин:пароль" (кириллица уходит как ???????) —
#    собрать заголовок вручную:
AUTH=$(printf '%s:%s' "$ONEC_IB_USER" "$ONEC_IB_PASS" | base64 -w0)

# 2. Кириллица в URL-пути (имя объекта) — процентно закодировать САМОМУ:
ENC=$(python3 -c "import urllib.parse; print(urllib.parse.quote('Номенклатура'))")

# 3. JSON-тело POST с кириллицей — писать в файл и слать --data-binary @файл,
#    НЕ инлайн-строкой в -d (аргумент argv тоже теряет кириллицу).
```

### 3.2 Health — платформа и сессия живы

```
curl -s -H "Authorization: Basic $AUTH" http://<адрес>/hs/aidbg/health
# {"version":"...", "session_user":"...", "privileged_allowed":false, ...}
```

### 3.3 OData — состав интерфейса включён и роль есть

```
curl -s -H "Authorization: Basic $AUTH" "http://<адрес>/odata/standard.odata/\$metadata" | grep -c EntitySet
```
- `0` → состав пуст (см. §5, «Настройка стандартного интерфейса OData»), роль тут ни при чём.
- запрос данных без роли → `401` даже с верным паролем (см. §5).

### 3.4 Реальное чтение данных

```
curl -s -H "Authorization: Basic $AUTH" \
  "http://<адрес>/odata/standard.odata/Catalog_${ENC}?\$top=3&\$format=json"
```

### 3.5 Произвольный запрос через расширение

```
echo '{"text":"ВЫБРАТЬ ПЕРВЫЕ 3 Ссылка, Наименование ИЗ Справочник.Номенклатура","mode":"user"}' > /tmp/q.json
curl -s -H "Authorization: Basic $AUTH" -H "Content-Type: application/json; charset=utf-8" \
  -X POST http://<адрес>/hs/aidbg/query --data-binary @/tmp/q.json
```

## 5. Настройка состава OData (`Настройка стандартного интерфейса OData`)

НСИ и администрирование → Синхронизация данных → «Настройка стандартного интерфейса OData»
(искать через глобальный поиск сверху — быстрее навигации по разделам) → вкладка «Состав» →
«Загрузить метаданные» (на большой конфигурации ERP — до минуты ожидания на первый раз, не
зависание) → отметить нужные объекты (например «Номенклатура и связанные объекты») →
Сохранить и закрыть.

## 6. Диагностика по коду ответа (не гадать)

| Ответ | Причина | Что делать |
|---|---|---|
| Системная ошибка 1С «resource not found» (не HTTP 404) | OData вообще не публикована в `.vrd` | Публикация (§4) |
| `401`, даже с верным паролем | Нет роли `Удаленный доступ (OData)` | §2 |
| `200`, пустой `<workspace>`, 0 EntitySets в `$metadata` | Роль есть, состав пуст | §5 |
| `503` на `/hs/aidbg/*` при неудачной auth | Не баг публикации — сеанс не создан (нормально для расширений) | Проверить Basic-auth (§3.1) |
| DESIGNER `exit 1`, лог и вывод ПУСТЫ (не текст ошибки) | GUI-приложение не получило оконный хендл ИЛИ кириллица в пути | §A.2, пункты 1–2 |
| DESIGNER: «Error locking infobase for configuration» | Другой `1cv8.exe`/Конфигуратор уже держит базу | `Get-Process -Name 1cv8,1cv8c`, закрыть/`Stop-Process` |
| `/LoadConfigFromFiles ... /UpdateDBCfg` в одной команде → «Error in command-line options» | Это два разных действия DESIGNER | Два отдельных вызова (§A.2 п.3) |
