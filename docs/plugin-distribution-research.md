# Доставка toolkit плагином: исследование и решение

**Статус:** решение принято — делать плагин. **Исполнение отложено**: перед реализацией обязателен
блок исследования (см. §3). Дата фиксации: 2026-08-24.

**Мотив:** сегодня toolkit корректно работает только когда текущий каталог — сам репозиторий.
Реальная работа идёт в каталогах проектов и клиентов.

---

## 1. Почему привязка к каталогу — факты, а не ощущение

Замерено на рабочей машине (macOS), четыре независимые привязки:

| Слой | Как сейчас | Что ломается вне каталога |
|---|---|---|
| Скиллы | `.claude/skills/` внутри репозитория | проектные скиллы грузятся только под своим каталогом |
| MCP | `.mcp.json` в корне, пути через `${ENV}` | сами пути уже переносимы, но файл проектный |
| Хук BSL | `python3 scripts/bsl_guard.py` | **относительный путь** — вне каталога не находится |
| CLI и модуль | `bin/1c-meta`, `onec_metadata/` | в SKILL.md указаны относительно корня репозитория |

Вывод: перенос одних скиллов в `~/.claude/skills/` закрывает примерно четверть задачи.
Хук и CLI останутся сломанными.

## 2. Почему именно плагин

Плагин ставится глобально (`scope: user`), несёт скиллы, команды, хуки и MCP-профиль одним
версионируемым артефактом, обновляется через marketplace/git. Главное — внутри плагина доступен
`${CLAUDE_PLUGIN_ROOT}`, то есть хук и путь к CLI перестают зависеть от текущего каталога: чинится
ровно то, что сейчас ломается. Прецеденты на машине уже есть (`ponytail`, `openai-codex`,
`claude-plugins-official`), механика проверена в бою.

Рассмотренные и отклонённые как самостоятельное решение:

- **копия/симлинки скиллов в `~/.claude/skills/`** — лечит один слой из четырёх, плодит вторую
  копию либо ломается при переезде репозитория; не переносится на другие машины;
- **указатель в `CLAUDE.md` проектов** — минимальная мера «на сегодня», не автотриггер;
- **ничего не делать** — работа вне каталога toolkit уже стала регулярной.

Оба первых пункта остаются допустимой временной мерой до плагина, но не заменяют его.

## 3. Что исследовать ДО реализации

1. **Существующие плагины и расширения по 1С** в экосистемах Claude Code / Cursor / VS Code /
   OpenAI-совместимых харнессов: что уже сделано, какие функции покрыты, чей подход к упаковке
   удачен, где чужие грабли. Не изобретать, если есть рабочий образец.
2. **Лучшие практики построения и распространения плагинов**: структура манифеста, версионирование,
   marketplace против git-установки, канал обновлений, что считается «правильным» пакетом.
3. **Онбординг на разных ОС.** Контур включает macOS (эта машина) и **Windows** (Work PC, Server PC).
   Проверить пути, права, кодировки, запуск Python и Java, поведение хуков в обеих ОС.
4. **Разные модели ИИ и харнессы.** Ключевая архитектурная развилка — см. §4.1.
5. **Как ложится слой локализации** — см. §4.2. Это самый рискованный пункт.

## 4. Открытые вопросы проектирования

### 4.1. Плагин не должен ломать агент-агностичность

Toolkit намеренно построен как «агент-агностичное ядро → адаптеры»: канон в `AGENTS.md` по
открытому стандарту agents.md, из него `build.sh` генерирует конфиги под Claude Code, Gemini,
Codex, Cursor, Copilot, Cline, Windsurf. Плагин Claude Code — **ещё один канал доставки, а не
замена ядру.** Иначе теряется поддержка остальных харнессов и смысл `core/`.

Проектировать так: `core/` остаётся источником истины, плагин собирается из него тем же
`build.sh` как отдельная цель. Дублирование содержимого в репозитории — признак ошибки сборки.

### 4.2. Слой локализации — главный конфликт с плагином

Контракт `docs/SKILL_LOCALIZATION.md` сегодня устроен так: generic-скилл ставится в
`~/.claude/skills/<skill>/`, а репозиторий компании (например `claude-1c-team`, корпоративные локализации)
своим onboard-ом раскладывает файлы в `references/local/` **внутри установленного скилла**;
generic обновляется целиком, `references/local/` при этом сохраняется.

С плагином это не работает как есть: плагин живёт в
`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, каталог версионный и заменяется при
обновлении — всё, что локализация туда положит, будет затёрто. Нужен другой механизм.

Кандидаты (решать при исполнении, ни один пока не выбран):

- **вынести локализацию из тела скилла** в отдельный корень, который скилл ищет по конвенции или
  через переменную окружения (по аналогии с уже используемым `${ONEC_SRC_DIR}` в MCP-профиле);
- **локализация как отдельный плагин-компаньон** — плагины компонуются, обновляются независимо;
- **проектный уровень**: локализация лежит в репозитории проекта, скилл читает её из каталога
  проекта, а не из своей установки. Ближе всего к тому, как локализация и рождается.

Требования к любому решению: обновление generic не затирает локализацию; локализация не правит
generic-файлы; при противоречии локальное побеждает; несколько компаний/проектов на одной машине
не конфликтуют между собой.

### 4.3. Прочее, что придётся решить

- **Python-часть.** `onec_metadata` тянет `lxml`. Либо `uv run` со своим окружением, либо вендоринг.
  На Windows это отдельная проверка.
- **Внешние бинарники.** BSL Language Server (`.jar`) требует JRE — на этой машине Java **нет**
  (обнаружено 24.08). Плагин должен деградировать честно, а не падать.
- **Секреты и приватность.** Пути к базам, креды, кейсы клиентов в плагин не кладутся — остаются
  во внешнем `.env`/keychain. Репозиторий публичный, приватные материалы туда попасть не должны.
- **Коллизии имён.** Уже сейчас `1c-expert` существует и глобально, и в toolkit; система разводит
  их префиксом `claude-1c-toolkit:1c-expert`. При массовом переносе коллизий станет больше —
  проверить, как их разводит пространство имён плагина.

## 5. Критерии готовности

- 1С-скиллы, хук BSL и CLI `1c-meta` работают из произвольного каталога на macOS и на Windows;
- локализация компании подхватывается и **переживает обновление** плагина;
- `core/` остаётся единственным источником истины, остальные харнессы не деградировали;
- установка и обновление описаны одной командой, откат возможен;
- в публичный артефакт не попало ничего приватного.

## 6. Пока плагина нет

Временная мера: указатель на 1С-скиллы в `CLAUDE.md` тех проектов, где ведётся работа по 1С,
и при необходимости симлинки `1c-metadata` / `1c-dev` в `~/.claude/skills/`.

## 7. Дубли скиллов на рабочей машине — ревизия 24.08.2026

**Правило владельца:** на машине держим **одну копию** скилла. Устаревшая копия — удаляется;
если в копии есть улучшения — они переносятся в toolkit, и только потом копия удаляется.

### Что найдено

Пересечение имён между `~/.claude/skills/` и `core/skills/` — ровно одно: `1c-expert`.
Плюс самостоятельно устаревший `1c-<компания>` (старый объединённый).

| Скилл | Вердикт | Основание |
|---|---|---|
| `1c-expert` (глобальный) | **старая копия, удалён** | состав файлов совпадает с toolkit; единственное отличие — в глобальной копии ОТСУТСТВУЕТ блок «Локализация», который в toolkit есть. Копия от 08.07, toolkit от 24.07. Уникального содержимого нет — переносить нечего |
| `1c-<компания>` (старый объединённый) | **устарел, удалён** | сам себя объявляет: «УСТАРЕЛ (2026-06-18), разделён на три скилла, оставлен как указатель и будет удалён» |
| `1c-<компания>-dev`, `1c-<компания>-analyst` | **оставлены, нужна миграция** | см. ниже |

Удаление сделано через `git rm` в репозитории `vgtitov/claude-skills` (обратимо, не закоммичено).

**Побочный эффект, который надо помнить:** `1c-expert` теперь доступен только под каталогом
toolkit. До плагина глобальную доступность можно вернуть симлинком на `core/skills/1c-expert`
— это по-прежнему одна копия, а не вторая.

### `1c-<компания>-*` — не дубли, а форки под миграцию

Проверено пофайлово: `1c-<компания>-dev` и toolkit-овский `1c-dev` делят пять generic-файлов
(`platform-ops`, `code-standards`, `performance`, `bsp-top-methods`, `ai-pitfalls`). Направление
расхождения — **toolkit новее и шире**: у него обобщённые формулировки и есть содержимое, которого
в форке нет (например ENFORCED-детектор `scripts/bsl_guard.py` в `performance.md`). Обратного, то
есть улучшений в форке, которых нет в toolkit, не обнаружено — **переносить в toolkit нечего**.

Отличия форка сводятся к константам компании: префиксы расширений `ан`/`ask`, режим совместимости
8.3.21, версия БСП 3.1.9.144, имена вроде `анСобытияФормСервер` и `ан…HTTP`, MCP `erp-1c` вместо
`onec-code`. Плюс собственные файлы: `erp-map.md`, `knowledge-map.md`, `project-conventions.md`,
`execution-workflow.md`.

Это ровно то, для чего заведён контракт `docs/SKILL_LOCALIZATION.md`: generic приходит из toolkit,
константы компании живут в `references/local/`. Сейчас же generic продублирован внутри форка и
поэтому устаревает.

**Задача (в очередь, вместе с плагином):** мигрировать `1c-<компания>-dev` и `1c-<компания>-analyst` на
контракт локализации — оставить в них только корп-специфичные файлы как `references/local/`,
generic брать из toolkit. Делать **вместе с решением по плагину** (§4.2), потому что вопрос один и
тот же: где физически живёт слой локализации, чтобы обновление generic его не затирало. Пока
решение не выбрано — форки не трогаем, они рабочие.
