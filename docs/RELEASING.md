# Как выпускать релизы

Релизы нужны, чтобы потребители пинили стабильную версию ядра, а собранные бинарные артефакты 1С (расширение
`ai_debug`) раздавались готовыми, а не собирались каждым вручную.

## Версии (SemVer)
Версия вида `vX.Y.Z`:
- **MAJOR (X)** — несовместимое изменение: переименование, смена структуры `core/`, ломающее правило, несовместимый
  формат движка метаданных.
- **MINOR (Y)** — новый навык, новый инструмент/MCP, новое покрытие метаданных, новый адаптер агента. Совместимо.
- **PATCH (Z)** — исправления, уточнения правил, доки, мелкие фиксы проверок.

## Когда выпускать релиз
- Появился заметный новый функционал (навык, MCP, покрытие метаданных, адаптер) — MINOR.
- Накопились исправления, которые командам стоит забрать — PATCH.
- Изменилось расширение `ai_debug` (BSL или структура) — обязательно релиз с новой сборкой `.cfe` (см. ниже).
- Ломающее изменение структуры или правил — MAJOR, с разделом в CHANGELOG про миграцию.

Не выпускай релиз на каждый коммит. Копи изменения в разделе `[Unreleased]` в `CHANGELOG.md`.

## Как выпустить (по шагам)

1. Обнови `CHANGELOG.md`: перенеси нужное из `[Unreleased]` в новый раздел
   `[X.Y.Z] - ГГГГ-ММ-ДД`.
2. Обнови локальный `main` через `git pull --ff-only`. Рабочее дерево должно быть чистым,
   а `HEAD` — в точности совпадать с `origin/main`.
3. Запусти guard из корня репозитория:

   ```bash
   python scripts/release_guard.py tag vX.Y.Z
   ```

   Он проверит строгий SemVer, отсутствие и возрастание тега, CHANGELOG, ветку и remote,
   выполнит полный набор тестов и создаст локальный аннотированный тег. Guard намеренно
   не делает push.
4. Проверь созданный объект и его коммит:

   ```bash
   git cat-file -t vX.Y.Z
   git show --no-patch --decorate vX.Y.Z
   git ls-remote --exit-code --tags origin refs/tags/vX.Y.Z
   ```

   Первые две команды должны показать аннотированный тег на ожидаемом коммите; последняя
   до публикации должна сообщить, что удалённого тега ещё нет.
5. Явно опубликуй только проверенный тег:

   ```bash
   git push origin vX.Y.Z
   ```

6. Дождись зелёного workflow `release.yml`. Он заново запускает полный набор тестов,
   проверяет, что аннотированный тег указывает на checked-out коммит из `origin/main`,
   и только затем создаёт GitHub Release с `ai_debug-src.zip`.
7. Если менялось расширение, **собери и приложи бинарник** (см. следующий раздел) —
   CI платформы 1С не имеет и `.cfe` собрать не может.

Если guard или workflow завершился ошибкой, тег не перемещают и не переиспользуют.
Исправление проходит через новый коммит и новую версию. Если локальный тег ещё не
публиковался и guard создал его на неверном коммите, его можно удалить локально,
устранить причину и повторить preflight; опубликованные теги неизменяемы.

Для нестандартного проверочного запуска можно передать собственную команду последним
аргументом:

```bash
python scripts/release_guard.py check vX.Y.Z \
  --verify-command uv run --no-project --with pytest pytest tests/ -q
```

## Контракт с потребительскими репозиториями

Toolkit хранит только общий механизм и не содержит URL, профилей, секретов или правил
конкретных организаций. Потребитель сам выбирает pin-файл, upstream URL, ветку,
обёртки хуков, CI и порядок review.

Проверка существующего пина:

```bash
python <toolkit>/scripts/consumer_pin.py check \
  --repo <upstream-git-url> \
  --pin-file <consumer-pin-file>
```

Безопасное обновление:

```bash
python <toolkit>/scripts/consumer_pin.py bump \
  --repo <upstream-git-url> \
  --pin-file <consumer-pin-file> \
  --tag vX.Y.Z
```

Helper требует строгий SemVer и существующий upstream-тег, атомарно меняет только
указанный pin-файл и никогда не коммитит, не пушит и не создаёт PR/MR. Потребительский
CI должен выполнять `check`; bump проходит отдельным review. Допустимо намеренно
оставаться на более старой версии — обязательна валидность пина, а не его свежесть.

## Сборка расширения `ai_debug` (на машине с платформой 1С)
Расширение `ai_debug` нужно для слоя данных `onec-data` (сервис под правами пользователя, только чтение). Исходник
лежит в `extensions/ai_debug/src` в формате 1C:EDT. Готовый `.cfe` собирается там, где есть платформа и 1C:EDT или
Конфигуратор (обычно Work PC, Windows):
1. Импортируй `extensions/ai_debug/src` как проект расширения в 1C:EDT (или загрузи в Конфигуратор как расширение).
2. Собери файл поставки расширения `ai_debug.cfe`. Это можно сделать и через toolkit: модуль
   `onec_metadata/apply/external.py` (`load_cfe` / `dump_cfe`) запускает пакетный режим Конфигуратора на машине с
   платформой. То же семейство команд собирает и внешние обработки/отчёты `.epf`/`.erf` (`build_external`).
3. Приложи `ai_debug.cfe` к соответствующему GitHub Release (кнопка Edit release → Attach binaries), рядом с
   `ai_debug-src.zip`.
4. В описании релиза укажи, на какой версии платформы и режиме совместимости собрано.

Так пользователи получают и исходник для правок, и готовый `.cfe` для установки.

## Git LFS — не используем (обоснование)
Проанализировано: в репозитории только текст (XML, BSL, Python, Markdown), самый крупный файл около 110 КБ, бинарных
файлов нет. Плюсы LFS (компактный клон при больших бинарниках) здесь не нужны, а минусы реальны: LFS усложняет клон и CI,
требует поддержки на всех зеркалах (в том числе корпоративный GitLab-форк) и упирается в квоты. Решение: **бинарные
артефакты (`.cfe`, при появлении `.epf`) держим в GitHub Releases, а не в git**, LFS не подключаем. Вернуться к вопросу
стоит только если понадобится версионировать в самом репозитории крупные бинарные фикстуры.

## Расширения проекта — не забывать
Если в toolkit появляется новое расширение 1С (по образцу `ai_debug`), его нужно вести так же: исходник в
`extensions/<имя>/src`, сборка `.cfe` на машине с платформой, приложение к релизу, строка в `CHANGELOG.md` и, при
необходимости, в `release.yml` (добавить упаковку его исходника в архив).
