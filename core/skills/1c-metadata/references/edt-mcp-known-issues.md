# Известные ловушки: EDT MCP, EDT + git, пакетный деплой расширения

Проверено на практике (EDT 2025.x, плагин EDT-MCP, платформа 8.3.27). Общее у всех пунктов одно:
операция НЕ выдаёт нормальной ошибки — она либо «таймаутит», либо возвращает успех, а результат
оказывается не тем, которого ждали. Поэтому проверяем результат, а не код возврата.

## EDT MCP: правка метаданных

**«Таймаут» при установке типа — это модальное окно EDT.** `modify_metadata` с установкой
`type` открывает в EDT диалог «разрешить менять тип», который ждёт клика пользователя. MCP-клиент
отваливается по таймауту, но **операция применяется**, как только человек нажмёт «Да». Правило:
при любой правке типа сразу предупреждать пользователя посмотреть в EDT и подтвердить окно (и снять
галочку «спрашивать снова») — тогда таймаутов нет вовсе. После правки типа проверять применение через
`get_metadata_details`, а не по ответу вызова.

**Формат описания типа различается для формы и метаданных.** У реквизита формы — всегда
`{types: [...]}`, одиночный `{kind: ...}` отвергается. У метаданного объекта — `{kind: 'CatalogRef',
ref: 'X'}` или `{kind: 'Ref', ref: 'Enum.Y'}`; форма `{kind: 'Ref', metadata: 'Catalog.X'}`
отвергается.

**Ссылочный тип на объект базовой конфигурации — только после заимствования.** Сначала
`adopt_metadata_object` (проект — базовая конфигурация, `fqn = Catalog.X`), затем `modify_metadata`
с типом. Без заимствования — «Cannot resolve the reference target», а `get_metadata_details` по
такому объекту отвечает «Object not found». Ссылки на объекты самого расширения и примитивные типы
ставятся сразу.

**Колонку реквизита-таблицы формы через MCP не создать** (`Form.F.Attribute.<Таблица>.Attribute.X`
не резолвится). Обход без правки метаданных: добавить колонку программно в `ПриСозданииНаСервере`
(`ИзменитьРеквизиты` + `Элементы.Добавить(..., Тип("ПолеФормы"))` + `ПутьКДанным`). Ловушка обхода:
к реквизитам формы, добавленным так, нельзя обращаться по имени — EDT даёт `undefined-variable` и на
сервере, и на клиенте, нужен `ЭтаФорма["Имя"]`; колонка таблицы значений через точку у строки
работает, потому что тип строки динамический.

**Параметр формы MCP не объявляет** — `create_metadata` на `...Form.Parameter.X` отвечает
«Unsupported form element kind». Это гейт «человек в EDT». Практическая оговорка: НЕобъявленный
параметр открытия всё равно доезжает в `Параметры` в `ПриСозданииНаСервере` и работает, так что ради
самой работоспособности бежать в EDT не обязательно — только ради соответствия стандарту.

**Права роли через `rights=[...]` работают**, включая явный запрет (`value: "unset"`) поверх
авто-выдачи. Но у роли, у которой ещё НЕТ файла `Rights.rights`, вызов падает с «Failed to persist
reference value RoleDescription». Обход: написать `Rights.rights` по образцу существующей роли
(в формате EDT: корень `<Rights ... xsi:type="Rights">`, пространство имён ролей, табы, перечисляются
только права со значением `true`) — EDT подхватывает файл с диска сама.

**Видимость подсистемы по ролям через MCP не настраивается вовсе** — в схеме свойств её нет.
Доступен только грубый `includeInCommandInterface=false` (скрыть у всех); тонкая настройка — человек в EDT.

**Проекты внешних объектов (`projectKind=externalObjects`) через MCP не редактируются** — «Could not
get configuration for project». Это не временная ошибка, а отсутствие поддержки: собрать через MCP
тестовую внешнюю обработку нельзя.

**`write_module_source` даёт ложный синтаксический отказ.** Встроенный пред-чекер считает блоки
построчно и спотыкается об однострочные `Если … Тогда … КонецЕсли;` и `Асинх Процедура` ГДЕ-ЛИБО в
модуле, выдавая каскад «Mismatched КонецПроцедуры» на строки ВНЕ правки. Если вставка заведомо
сбалансирована, а ошибки указывают на чужие строки — это ложь: ставить `skipSyntaxCheck: true` и
проверять по-настоящему (BSL Language Server + `get_project_errors`).

## EDT и git

**Файлы метаданных молча теряют содержимое при слиянии веток.** EDT держит модель конфигурации в
памяти и при сохранении переписывает `.mdo`/`.rights`/`.form` целиком; если модель осталась от прежнего
состояния ветки, на диск уходит устаревшее содержимое. Для git это обычная правка, а не конфликт,
поэтому при слиянии побеждает «старая» сторона.

**`git log -- <файл>` про такие потери ВРЁТ:** слияние, результат которого совпал с одним из
родителей, в истории файла не показывается — она выглядит чистой. Искать надо обходом состояний:
`git rev-list --reverse BASE..<ветка>` и сравнение блобов (`git rev-parse <commit>:<файл>`); массово —
файлы, чей блоб в ветке равен блобу точки ветвления.

**Автомерж двух веток, добавлявших элементы в одну форму, даёт не конфликт, а коллизию
идентификаторов.** Обе стороны «успешно» сливаются, элементы получают одинаковые `<id>`. После слияния
формы парсить XML и искать дубли id в пространстве элементов (элементы, расширенные подсказки и
контекстные меню нумеруются вместе; у реквизитов, команд и колонок нумерация своя — совпадения там
нормальны), переномеровать свою сторону от максимума+1. Отдельно проверять, что команды одной стороны
не съели команды другой и что все обработчики резолвятся.

**Профилактика:** короткие ветки, слияние основной ветки В свою до вливания, закрытый проект EDT при
переключении веток (иначе git не может перезаписать удерживаемые файлы и оставляет дерево из двух
веток), Refresh (F5) после переключения.

**`export_configuration_to_xml` задваивает элементы на больших заимствованных типовых формах**
(проверено на двух формах по 7000+ строк, независимо от чистоты каталога экспорта). Ещё один довод не
заимствовать типовые формы ради мелких доработок.

**Комбинированный `<synonym>` теряется при сборке `.cfe` из git.** Если записать несколько языков в
один элемент `<synonym>` с несколькими парами `key`/`value`, EDT это принимает — revalidate и
`get_project_errors` чисты, round-trip проходит, — но конвертер сборки расширения из исходников такой
синоним НЕ переносит: в собранном `.cfe` и в базе синоним пустой, объект показывает голое имя.
Проявляется только после сборки из git, не из модели EDT. **При любой программной вставке синонимов
эмитить сразу отдельный `<synonym>` на каждый язык.**

## Пакетный конфигуратор и программный деплой расширения

**Расширение, установленное программно, получает признак безопасного режима — и перехваты молча не
работают.** `LoadConfigFromFiles -Extension` + `UpdateDBCfg -Extension` (в том числе через
`scripts/designer_sync.py deploy-extension`) создают расширение с `БезопасныйРежим = Истина`, а в этом
состоянии аннотированные перехваты `&Вместо`/`&После`/`&Перед` НЕ исполняются. При установке через
Конфигуратор флаг снимается сам, поэтому ловушка видна только при пакетной установке.

Диагностика обманчива: расширение активно, объекты видны в `Метаданные.*`, `CheckConfig` проходит,
**экспортные методы модулей расширения вызываются нормально**, а перехваченный типовой метод просто
отдаёт исходное поведение. Ни ошибки, ни записи в журнале регистрации.

Лечение — постдеплойный идемпотентный сценарий (нужно право «Администрирование»):

```bsl
Для Каждого Расширение Из РасширенияКонфигурации.Получить() Цикл
    Если Расширение.Имя = ИмяРасширения И Расширение.БезопасныйРежим <> Ложь Тогда
        Расширение.БезопасныйРежим = Ложь;
        Расширение.Записать();
    КонецЕсли;
КонецЦикла;
```

Смежное: повторный деплой в УЖЕ существующее расширение флаг не возвращает (он ставится только при
создании); назначение установленного расширения сменить нельзя («если расширение влияет на структуры
данных») — только удалить и поставить заново.

**«Ошибка формата потока» при обновлении ИБ из EDT = повреждено само расширение в базе,** а не база и
не платформа. Различается тремя прогонами пакетного конфигуратора: `DumpConfigToFiles` без ключа
(проходит — база цела), он же с `-Extension <Имя>` (падает — расширение битое), он же на новой пустой
базе (проходит — платформа цела). При падении `/Out` пустой, сообщение видно только в GUI, так что
код возврата 1 без лога — уже сигнал. Лечение: `DeleteConfigExtension` → `LoadConfigFromFiles
-Extension` → `UpdateDBCfg -Extension`. Перед удалением — копия базы: удаление расширения уносит
данные в его реквизитах.

**Пакетный сеанс висит с ровным CPU и пустым `/Out`** — обычно некомпилируемый модуль в накатанной
конфигурации, а не защита от опасных действий. Прогонять `CheckConfig` сразу после загрузки, а не
гадать по таймауту.

**Сборка расширения из файлов в формате Конфигуратора: шесть отказов подряд.**
1. Заимствованному объекту обязателен блок `InternalInfo` с `GeneratedType` — иначе «Отсутствует
   внутренняя информация». Значит заимствование делаем клоном уже работающего заимствованного объекта.
2. `StringQualifiers` без `AllowedLength` трактуется как `Fixed`, а фиксированная строка длиннее 100
   символов запрещена — дописывать `Variable`.
3. `InputByString` донора тащит `StandardAttribute.Code`; при `CodeLength = 0` загрузка падает
   «неверное поле для ввода по строке» — строку убрать.
4. Первый дочерний элемент в пустой `<ChildObjects/>` CLI не добавляет — посеять один элемент кодом,
   дальше работает обычная операция.
5. **uuid заимствованных объектов должны быть уникальны в базе.** Файлы из выгрузки ЧУЖОГО расширения
   той же базы дают конфликт внутренних идентификаторов, и расширение **молча не применяется**:
   активно = Да, объекты в его конфигурации есть, а в сеансе их нет. Диагноз только в журнале
   регистрации, событие «Сеанс. Ошибка применения расширения конфигурации». Лечение — перегенерация
   uuid заимствованных объектов (значение `ExtendedConfigurationObject` не трогать).
6. Загрузка структуру БД не применяет — нужен отдельный `UpdateDBCfg -Extension` БЕЗ ключа `-Server`.

## BSL Language Server

**`InvalidCharacterInFile` на ровном месте** — длинное тире (U+2014) в комментарии `.bsl`. В
комментариях писать ASCII-дефис; кавычки-ёлочки допустимы, диагностика ловит именно тире-подобные символы.
