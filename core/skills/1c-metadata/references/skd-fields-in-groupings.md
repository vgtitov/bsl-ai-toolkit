# СКД: вывод поля в группировку/таблицу — правило допустимости и пробелы агента

Обезличенный конспект. Закрывает конкретный класс провала: агент добавил поля в запрос и в набор данных СКД,
поле есть в схеме — но при компоновке падает `Поле "X" не может быть использовано в группировке "A, B, C"`,
либо колонка молча не выводится. Дальше агент начинает «лечить» это ресурсами `Максимум(...)` и переделкой
структуры отчёта в плоскую — оба хода неверны.

Источники переработки: книга по разработке сложных отчётов на СКД (разделы «Поля-реквизиты», «Ресурсы»,
«Расположение реквизитов», «Использование автополей», «Особенности группировки детальных записей»),
методические материалы по настройке отчётов пользователями.

---

## 1. Правило допустимости (главное)

В **выбранные поля группировки** можно поместить поле только если оно одно из трёх:

| Класс поля | Что это | Как объявляется |
|---|---|---|
| **Поле группировки** | входит в `groupItems` этой группировки | настройка структуры |
| **Реквизит поля группировки** | подчинённое поле, доступное «через точку» от поля группировки | `dataPath` с точкой |
| **Ресурс** | агрегат по детальным записям группы | `totalField` (`ПоляИтога`) |

Всё остальное → `Поле ... не может быть использовано в группировке ...`. Ошибка про **класс поля**, а не про тип
данных и не про отсутствие агрегата: добавление `totalField` лечит её только если поле действительно должно быть
итогом.

## 2. Поля-реквизиты — то, что агент обычно не знает

Плоская колонка запроса становится **реквизитом другого поля**, если в описании полей набора данных задать
`dataPath` через точку от этого поля. Имя колонки запроса (`field`) при этом не меняется.

```xml
<field xsi:type="DataSetFieldField">
    <dataPath>Номенклатура.НомерСертификата</dataPath>  <!-- было: НомерСертификата -->
    <field>НомерСертификата</field>                      <!-- колонка запроса, как есть -->
</field>
```

Последствия — ровно те, что нужны:

* поле выводится в любой группировке, где есть `Номенклатура`, **без ресурса и без агрегата**;
* в доступных полях отчёта оно показывается как реквизит `Номенклатуры` — пользователь находит его там, где ждёт;
* автополе группировки его **не подхватывает** (правило автополя: «не являются реквизитами других выбранных
  полей») — то есть оно не превратится случайно в поле группировки и не размножит строки.

Ограничение: владелец (`Номенклатура`) должен присутствовать в наборе данных; имя реквизита не должно
конфликтовать с реальным реквизитом объекта этого типа.

### Обязательный парный параметр — `РасположениеРеквизитов`

По умолчанию **«Вместе с владельцем»**: реквизиты сваливаются в колонку владельца, и внешне это выглядит как
«поле не вывелось». Для отдельных колонок нужно `Отдельно` (в XML —
`<dcscor:parameter>РасположениеРеквизитов</dcscor:parameter>` → `Separately`) в `outputParameters` варианта.
Варианты: `Вместе` / `Отдельно` / `Вместе с владельцем` (умолчание) / `В специальной позиции`.

**Диагностический приём:** если в отчёте уже есть работающие колонки вида `Владелец.Реквизит`
(`Номенклатура.Артикул` и т. п.) — механизм реквизитов там уже настроен, и новые поля надо заводить так же.
Это самый дешёвый способ узнать «как принято в этом отчёте», не читая всю схему.

## 3. Почему ресурс здесь — неверный инструмент

* В структуре **Таблица** строки и колонки — группировки, а **в ячейках на их пересечении выводятся ресурсы**.
  Поле, сделанное ресурсом, уходит в матрицу и дублируется по каждой колонке (по каждой валюте/цене/складу), а не
  становится колонкой строки. Визуально это не то, что просили.
* Ресурс — это агрегат по всем детальным записям группы. Если запрос уже гарантирует одно значение на строку
  (антисоединение, `ПЕРВЫЕ 1`, связь 1:1), агрегат — чистая лишняя работа на каждой группе.
* **Дубль ресурса недопустим:** два `totalField` с одинаковым `dataPath` без разграничения по `<group>` — это два
  выражения одного ресурса для одной группировки. Схема становится невалидной, а диагностика платформы уводит
  в сторону (ругается на соседние поля).
* `Рассчитывать по…` (`<group>`) сужает ресурс до перечисленных группировок; пустое значение = «для всех».
  Ограничивать через `<group>` имеет смысл, когда итог по другим разрезам бессмыслен, а **не** как попытка
  починить ошибку группировки — она так не чинится.

## 4. Матрица выбора приёма

| Задача | Приём | Цена |
|---|---|---|
| Показать атрибут объекта рядом с ним в кросс-таблице | **поле-реквизит** (`dataPath` через точку) | 0 — кардинальность и число группировок не меняются |
| Значение должно ещё и разбивать строки | добавить в `groupItems` группировки | растёт число группировок, возможно размножение строк |
| Нужен именно итог (сумма/макс/кол-во) в ячейке таблицы | `totalField` | агрегация по каждой группе |
| Нужен линейный список без группировок | группировка **Детальные записи** (пустой список полей группировки) | теряется структура клиента — применять, только если это и есть требование |

Отдельно: **строка неограниченной длины** не может быть полем группировки (и полем отбора). Как реквизит
в выборе — выводится. Если такое поле планируется в группировку/отбор — задать длину при создании реквизита.

## 5. Порядок действий, который экономит итерации

1. Открыть схему и посмотреть, **как выводятся уже работающие неагрегатные колонки** этой же группировки
   (`grep '<dcsset:field>'` внутри нужного `row`/`column`). Скопировать их класс поля.
2. Проверить `outputParameters` варианта на `РасположениеРеквизитов`.
3. Завести новые поля тем же классом. Заголовок задавать явно (`<dcsset:title>`), иначе он берётся из `dataPath`.
4. Не трогать `settingsVariant` клиента структурно: добавление в `<dcsset:selection>` — безопасно, перестройка
   структуры — нет.
5. Скомпоновать и проверить **по факту вывода** (выгрузка результата в текст + поиск заголовков), а не по
   «схема загрузилась без ошибок».

## 6. Пробелы агента, которые этот кейс вскрыл

| Пробел | Чем обернулся | Чем закрыт |
|---|---|---|
| Не знал класса «поле-реквизит» и что он задаётся точкой в `dataPath` | несколько итераций с ресурсами и переделкой структуры | раздел 2 |
| Считал ошибку «не может быть использовано в группировке» ошибкой про агрегат | добавлял `Максимум(...)` — не помогало | раздел 1 |
| Не знал, что в структуре «Таблица» ресурсы идут в ячейки пересечения | ждал ресурс в виде колонки строки | раздел 3 |
| Не знал про `РасположениеРеквизитов` и умолчание «Вместе с владельцем» | риск «поле есть, но невидимо» | раздел 2 |
| Не проверял схему на дубли `totalField` после правок | невалидная схема + ложная диагностика | раздел 3 |
| Не сверялся с уже работающими полями того же отчёта | искал ответ в общих рассуждениях вместо образца рядом | раздел 5, п. 1 |
| Правило автополя (реквизиты не попадают в автополе группировки) | не мог объяснить, почему одни поля размножают строки, а другие нет | раздел 2 |
| Пытался заменить структуру клиента на плоскую ради обхода ошибки | лечение симптома, потеря требований клиента | раздел 4 |

## 7. Проверки, которые стоит гонять на схеме СКД после программной правки

```bash
# дубли ресурсов
grep -o '<dataPath>[^<]*</dataPath>' Template.xml | sort | uniq -d
# класс полей в конкретной группировке — с точкой (реквизит) или без (плоское)
grep '<dcsset:field>' Template.xml
# расположение реквизитов задано?
grep -c 'РасположениеРеквизитов' Template.xml
```

Плюс обязательный round-trip: загрузка в тест-базу платформой → компоновка → выгрузка результата в текст →
поиск ожидаемых заголовков колонок.
