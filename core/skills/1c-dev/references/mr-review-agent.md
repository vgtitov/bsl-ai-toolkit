# Ревью MR агентом: порядок и границы

Для случая, когда человек просит проверить чужой merge request. Чек-лист и приоритеты: `review-checklist.md`, первый проход: `scripts/mr_review.py`.

## Порядок
1. Прочитать MR целиком: дифф, описание, тех-проект задачи, постановку. Не по памяти и не по пересказу автора. Чего не получил (нет ссылки, дифф обрезан), перечислить и не писать «проверено полностью».
2. Составить список замечаний. У каждого: уровень, файл и строка, причина, как исправить.
   - `блокер:` без исправления не вливаем;
   - `желательно:` можно влить без правки.
3. Показать список человеку-ревьюеру. В MR публиковать комментарии по строкам (GitLab API) только после явной команды вида «опубликуй эти N комментариев в MR !123»; перед публикацией сверить проект, номер MR и актуальность строк. Общее замечание одним сводным комментарием. Большой разбор файлом, в MR итог и ссылка.
4. Следить за тредами: увидел ответ автора, перечитать исправленные строки и новый дифф после последнего коммита, потом предложить ревьюеру закрыть обсуждение.
5. Проверить описание MR по шаблону (задача, что сделано, как проверить, риски) и, что MR открыт на нужную ветку.
6. Если MR трогает интеграции и обмены, роли и права, регзадания, структуру данных, деньги или остатки, предложить второго ревьюера.

## Чего агент не делает
- Не одобряет MR и не вливает.
- Не закрывает чужие обсуждения и не меняет настройки проекта.
- Не пишет автору в личку вместо комментария в MR.
- Не публикует замечания без явной команды ревьюера.
- Не считает обсуждение с `блокер:` закрытым: его закрывает ревьюер.
