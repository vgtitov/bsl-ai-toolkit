# Рабочий цикл реализации: от тех-проекта до передачи кода

Контекст: артефакты приходят УЖЕ описанными (аналитик/архитектор подготовили ЧТЗ и тех-проект, тех-лид дожал
технические вопросы). Разработчик отдаёт их AI. Дальше — этот цикл.

## Разделение ролей в фазе разработки
- **AI (ты):** декомпозиция тех-проекта на атомарные задачи → инструкции разработчику по НЕ-коду → написание кода →
  проверка и тесты → финал prod-ready → передача.
- **Разработчик (человек):** создаёт в IDE (EDT или Конфигуратор) метаданные, формы, макеты, СКД, роли, реквизиты,
  подписки; применяет код AI; валидирует в IDE и грузит в ИБ; владелец осознанного принятия.
- **Структурные правки инструментом (`1c-metadata`/`onec_metadata`):** часть метаданных/форм/СКД/прав AI может
  менять сам byte-perfect (форматы Конфигуратора И EDT) — но ТОЛЬКО в пределах карты покрытия
  (`onec_metadata/COVERAGE_MAP.md`), на ТЕСТ-базе с round-trip-verify; результат подтверждает разработчик в IDE.
  Виды объектов ВНЕ карты — по-прежнему человек в IDE. Это не отменяет IDE-гейт, а даёт второй путь под гарантии инструмента.
- **EDT-контур с `edt-mcp` (DitriX):** дополняет `1c-metadata`. Профиль edt-mcp — каскадный рефакторинг через
  EDT (rename/delete существующих объектов с починкой ссылок в формах/BSL/метаданных) + ошибки проекта/валидация
  запросов. Установку типа edt-mcp **делает**, но EDT спрашивает согласие модальным окном («Разрешить менять тип» /
  «Разрешить на сессию») — прежнее «виснет по таймауту» оказалось этим диалогом, а не ограничением (пилот-правило:
  диалоги согласия EDT не подавлять). Права роли edt-mcp не пишет («нет модели прав»). Итог по инструментам:
  - рефакторинг существующего (rename/delete) → **edt-mcp**;
  - **права роли** → `1c-metadata` `role grant` (нужен объект-образец в роли);
  - **тип** → `1c-metadata` `edit-type` (расширен 15.07): задаёт/меняет тип реквизита, **измерения/ресурса**
    регистра и **самого объекта** (`--member` опущен: параметр сеанса/константа/определяемый тип); строит блок
    типа и квалификатор (`--length` строка, `--precision`/`--scale` число) **С НУЛЯ** на бестиповом поле; оба формата,
    byte-perfect. Новым элементам удобнее сразу с типом (`add-child`/`add-attribute`). Составной тип (список типов) тоже
    делает `edit-type`; правка состава **определяемого типа** пока вне инструмента. Остаётся человеку: **новый элемент EDT-формы** (P4.3). См. `COVERAGE_MAP.md`.
  Полное дерево выбора — в `AGENTS.md`/`CLAUDE.md` контура.

## Шаг 0. Понять вход и сверить по коду (не домысливать)
- Прочитать ЧТЗ (что/зачем, критерии приёмки) и тех-проект (слои, контракты/DTO, reuse, НФТ).
- Сверить по РЕАЛЬНОМУ коду через MCP (`find_object`→`search`→`read_module`): что уже есть, как устроена типовая,
  какие объекты/модули затронуты, нет ли готового в БСП/расширении (reuse-first).
- Техническая неопределённость/пробел в тех-проекте → вернуть тех-лиду/архитектору КОНКРЕТНЫЙ вопрос, не домысливать.

## Шаг 1. Декомпозиция на атомарные задачи
Разбить тех-проект на УПОРЯДОЧЕННЫЙ список атомов с зависимостями. Каждый атом — ОДНО конкретное проверяемое
действие с критерием готовности. Пометить исполнителя:
- **[Разработчик/IDE]** — создание/изменение метаданных, форм, макетов, СКД, ролей, реквизитов, подписок (не-код).
- **[AI/код]** — написание/правка `*.bsl` (логика).
Порядок: сначала [Разработчик] создаёт объекты, на которые опирается код, затем [AI] пишет код.

## Шаг 2. Инструкции разработчику по НЕ-коду (до написания кода)
Выдать точный список «создай в IDE», потому что код к этим объектам привяжется и без них не скомпилируется:
тип объекта; имя с префиксом расширения; реквизиты (имя, тип, длина/точность, индексируемость); формы и реквизиты
форм; регистры (измерения/ресурсы/периодичность); роли/права/RLS; подписки на события; место в дереве метаданных.

## Шаг 3. Реализация кода
Писать BSL по атомам, сверяя каждый по MCP (сигнатуры/объекты — не по памяти): конвенции проекта
(`conventions-template.md`); reuse-first БСП (`bsp-reuse.md`); производительность/кэш (`performance.md`);
стандарты (`code-standards.md`); prod-ready.
- **EDT-контур:** код кладётся в `*.bsl` расширения в репозитории.
- **Конфигуратор-контур, точечный dump/load (предпочтительно):** `scripts/designer_sync.py` — AI сам получает
  из базы файлы на редактирование и загружает их назад **по конфигурации И по расширениям**. Цикл: выгрузить
  из базы разработчика (или тест-базы) ТОЛЬКО затрагиваемые объекты (`dump --objects "ОбщийМодуль.X,..."` или
  `--ext Имя` для расширения; дот-нотация; объекты определить заранее по клонам через MCP), git init/commit
  в каталоге выгрузки, AI правит `.bsl` + BSL LS, назад — `load --changed`.
  - **Сначала договорись с разработчиком о формате работы** (какая база — своя/тест/предпрод, какие объекты
    выгружаем, кто и когда закрывает интерактивный Конфигуратор, как именуем помещение в хранилище). Без этой
    договорённости dump/load в чужую базу не запускаем.
  - Дальше разработчик в Конфигураторе проверяет: **«Сравнить конфигурацию → с конфигурацией базы данных»**
    (увидеть ровно наши изменения глазами), синтакс-контроль, тест, помещение в хранилище (комментарий AI
    формулирует по диффу).
  - **База с хранилищем — цикл целиком через `designer_sync`** (с разрешения разработчика на список объектов):
    `repo lock --objects …` (`-revised` сам заберёт свежую версию) → `dump` (актуальный код — ИЗ БАЗЫ, клоны
    могут отставать) → правка + BSL LS → `load` → **повторный `dump` и сверка с правкой** → `updatedb`
    (разрешение) → смоук → `repo commit --comment` (только по явному «помещай»). Креды хранилища —
    `ONEC_REPO_PATH_/USER_/PASS_<КЛЮЧ>`, логин ИБ — `ONEC_IB_USER_<КЛЮЧ>`.
  - ⚠ **Ложный успех загрузки/выгрузки — не верить `exit=0` и `[ok]`:**
    - точечная выгрузка (`-listFile`) отдаёт форму БЕЗ `<Events>` и `Form/Module.bsl` — формы сверять только по
      полной выгрузке (иначе ложное «формы в хранилище нет»); модули объектов отдаются верно;
    - точечная загрузка ориентируется на `ConfigDumpInfo.xml`, а не на файлы: из каталога частичной выгрузки
      может не загрузить ничего, а из старой полной — ОТКАТИТЬ объект к версии в `ConfigDumpInfo`;
      каталог выгрузки для load — только свежий dump этой же базы, без удалённого `ConfigDumpInfo.xml`;
    - `Configuration.xml` в `-files` без всех `Ext/*` корня СТИРАЕТ модуль сеанса, модули приложения,
      командный интерфейс и поддержку; load `exit=0`, обратная выгрузка пустой `Ext` просто не отдаёт.
      Симптом: «Попытка получения неинициализированного значения параметра сеанса» и панель разделов сверху.
      Корень грузить только вместе со всем `Ext/` из свежей выгрузки; сверку делать по СПИСКУ ожидаемых файлов;
    - формы больших документов (напр. `ЗаказКлиента`) могут не пережить пакетный round-trip — правка
      `Documents/<Док>.xml` тянет формы; падает атомарно, база цела.
  - **Что `designer_sync` проверяет сам** (отказ или предупреждение, без подключения к базе):
    - `load`: xml объекта (или `Configuration.xml`) в списке без всех файлов его `Ext/` из каталога
      выгрузки — отказ ДО запуска с перечнем недостающих; итог load печатается как «загружено, не
      проверено» — вердикт по повторной выгрузке;
    - `dump --objects`: форма, у которой события пропали относительно прошлой выгрузки того же каталога
      или события есть, а `Form/Module.bsl` нет, — ошибка «выгрузка формы неполная»; любые формы
      в точечной выгрузке — предупреждение;
    - учётка: без `--contour` ключ берётся из имени базы (`сервер\база` → `БАЗА`), серверной базе без
      учётки — отказ; с `--host` обязателен `ONEC_1CV8_BIN` (путь к 1cv8 на сервере); лог `/Out` прошлого
      запуска удаляется до старта;
    - `--host`: каталог уезжает на сервер zip-ом (кириллические имена не теряются на хосте с локалью
      en-US) со сверкой числа файлов;
    - после `deploy-extension` — предупреждение про безопасный режим расширения; после загрузки
      `ScheduledJobs/*` — подсказка про новое регламентное задание, которое планировщик не запускает,
      пока его не пересохранить.
  - Гейты: платформа сама не даст загрузить незахваченный в хранилище объект и запрещает полную загрузку
    в базу с хранилищем (грузим только `-files`); структуру вне карты покрытия `1c-metadata` создаёт человек;
    интерактивный Конфигуратор на время dump/load закрыт. ⚠ prod-базы не трогаем (см. реестр баз, `env=prod`).
- **Конфигуратор-контур, без обвязки (фолбэк):** код оформляется как готовый ФРАГМЕНТ для вставки в Конфигуратор
  (модуль/область/место); AI не коммитит, переносит разработчик.

## Шаг 4. Проверка и тесты (до передачи)
- **BSL Language Server:** синтаксис + стандарты ИТС. `Error` — блокер; `Vulnerability`/`Security Hotspot` —
  обязательны к разбору; `Code smell` — рекомендация. До 3 циклов автоисправления.
- **Сверка с тех-проектом и критериями приёмки ЧТЗ:** всё ли реализовано, нет ли расхождений с контрактами/DTO.
- **Собственные проверки сложных мест** (без запуска платформы): разбор граничных случаев; проверка логики запроса
  на МОДЕЛЬНЫХ данных; пошаговый разбор алгоритма; транзакции/порядок блокировок. Где есть тест-фреймворк
  (**xUnitFor1C / Vanessa**) — подготовить исполняемые тест-сценарии и отдать разработчику на прогон.
  **Честно:** BSL не исполняется в среде AI — пишутся тесты и проверяется статически/логически; прогон в ИБ — за разработчиком.

## Шаг 5. Финал и передача разработчику
Когда все проверки зелёные и версия production-ready — передать ПАКЕТ:
1. Что создать в IDE — финальный чек-лист объектов.
2. Код — куда вставить (модуль/область/место) или какие `*.bsl` изменены.
3. Как проверить в IDE: проверка конфигурации/синтаксический контроль (Конфигуратор) или валидация EDT.
4. Какие тесты прогнать и ожидаемый результат по критериям приёмки.
5. Как загрузить в ИБ.

## Шаг 6. Ветвление и путь до прод (EDT-контур, git-flow)
В EDT-контурах (репо в GitLab, напр. пример расширения) работаем через git-flow, не коммитим прямо в `develop`/`main`:
- `feature/*` (или `fix/*`) от `develop` → **MR в `develop`**; на MR CI прогоняет валидацию (напр. lint матрицы +
  dry-run гейт целостности). Договорённость по формату/веткам — с тех-лидом контура.
- **Релиз:** тех-лид льёт `develop` → `main`; push в `main` → CI авто-собирает и публикует артефакт (`.cfe`).
- Затем обновляют **предпрод**, проверяют; если ок — **прод**. Тестовая сборка ветки без релиза — Run pipeline.
- Точные правила CI/веток конкретного репо — в его `AGENTS.md`/`CLAUDE.md` и `.gitlab-ci.yml` (модель может ещё
  донастраиваться — напр. MR-гейт готов, но включается по мере перехода команды на MR).
- СНГ-контур (Конфигуратор + хранилище 1С): версионирование через хранилище, git — read-only зеркало; там AI не коммиттер.

## Шаблоны
**Атомарная задача:** `ID · название · исполнитель [Разработчик/IDE]|[AI/код] · зависит от · действие · критерий
готовности · ссылки`.
**Инструкция «создать в IDE»:** `Тип · Имя (префикс) · Реквизиты [имя:тип(длина/точн.), индекс] · Формы/реквизиты
форм · Регистры [измерения/ресурсы] · Роли/права/RLS · Подписки · место в дереве`.
**Пакет передачи:** `чек-лист объектов IDE · модули и места вставки · проверки IDE · тесты+ожидание · загрузка в ИБ`.
