# EDT + git: рабочий процесс команды, перешедшей с хранилища конфигураций

Для команд, у которых исходники 1С лежат в git в формате EDT. Здесь — процесс и то, обо что
спотыкаются в первые дни. Ловушки самого инструмента (молчаливая потеря метаданных при слиянии,
коллизия id при автомерже формы, пакетный деплой) — в `1c-metadata/references/edt-mcp-known-issues.md`.
Настройка рабочего места — `docs/edt-workstation.md`.

## Смена модели: ветка вместо захвата объекта

В хранилище объект **захватывают**, и пока он захвачен, никто другой его не правит. В git никто ничего
не блокирует: каждый работает в своей ветке, а расхождения сводятся при слиянии. Ветка — это, по сути,
отдельное хранилище, которое создаётся одним действием и живёт столько, сколько живёт задача.

Практическое следствие: чем короче ветка и чем чаще в неё вливается основная, тем меньше расхождений
придётся разбирать руками.

## Модель веток

| Ветка | Назначение |
|---|---|
| `main` | релизное/промышленное состояние, обычная разработка сюда не идёт |
| `develop` | интеграционная ветка: сюда собираются готовые изменения |
| `feature/<ключ задачи>` | новая функциональность и плановые доработки |
| `fix/<ключ задачи>` | исправление ошибки в рамках текущей разработки |
| `hotfix/<ключ задачи>` | срочное исправление, создаётся от `main` |
| `release/<версия или дата>` | стабилизация версии, если процесс это использует |
| `custom/<короткое описание>` | техническая работа: проверка новой версии платформы, обновление типовой, эксперимент |

Правила: ветка создаётся под **одну** задачу и после слияния удаляется; старую ветку не переиспользуют
под новую задачу; несколько независимых задач в одной ветке не смешивают. Разработка руками в `develop`
и `main` запрещена — в `develop` допустимы только получение изменений, интеграция и действия
ответственного по согласованной процедуре.

Сообщение коммита — ключ задачи и что сделано: `DEV1C-1660: добавлена проверка статуса заказа перед
отгрузкой`. «Правки», «изменения», «тест» — не сообщения.

## Цикл задачи

1. Переключиться на локальный `develop`, получить и слить изменения из удалённого.
2. Создать рабочую ветку от свежего `develop`.
3. Разработка — только в этой ветке; коммиты частые и осмысленные.
4. Перед сдачей: обновить `develop`, влить его **в свою ветку**, разрешить расхождения, проверить проект.
5. Отправить ветку и открыть merge request в `develop`.
6. Ревью → слияние. Прямой push в `develop` в целевом процессе закрыт защитой ветки.

Если команда только начинает и merge request ещё не обязателен, допустим временный упрощённый вариант:
влить свою ветку в локальный `develop` и отправить его. Даже тогда правило «разработка не в develop»
остаётся — иначе чужие изменения приезжают в общую ветку вместе с вашими.

Merge request содержит: ссылку на задачу, что сделано, как проверять, что затронуто, риски. Не
принимается, если задача не указана, не описано как проверять, попали лишние объекты или остались
неразрешённые расхождения.

## Что кладём в репозиторий, а что нет

Кладём: исходники конфигурации/расширения в формате EDT, внешние обработки и отчёты, если они часть
проекта, скрипты сборки и проверок, шаблоны настроек **без секретов**, документацию, `.gitignore`,
`README.md`, описание CI.

Не кладём: пароли, токены, ключи, реальные строки подключения к продуктиву, локальные базы и дампы,
кэши IDE, логи, heap dump, резервные копии, локальные настройки рабочего места.

## Типовые затруднения первых дней

**Правки сделаны прямо в `develop`.** Рука помнит одно хранилище. Перед любой правкой смотреть активную
ветку. Если уже наработали — IDE при создании ветки предложит зафиксировать, спрятать или отклонить
изменения; выбирать осознанно.

**Ветка создана не тем пунктом меню.** В EDT есть «Создать ветку» и «Переключиться на → создать».
Пользоваться первым: второй оставляет ветку без связей, которые потом настраивать руками.

**При создании ветки предлагают создать информационную базу.** Если базы большие и локальные копии не
используются — выбирать «не использовать», иначе IDE будет создавать копию на каждую ветку.

**Импорт проекта: пустой список.** Выбран «импорт существующего проекта», хотя репозиторий ещё не
склонирован. Нужен путь «клонировать по URL».

**Логин с доменом.** В корпоративный git заходят логином без почтового домена; пароль или токен
сохранять в защищённом хранилище IDE, иначе спросит ещё раз.

**Клон внутрь рабочей области.** Репозиторий кладётся в каталог репозиториев, не в `ws`.

**Тянут все ветки сразу.** При клонировании достаточно `main` и `develop`.

**Проект в красных крестиках.** Расширение не связано с базовой конфигурацией — указать её в свойствах
проекта.

**«Ошибка взаимодействия с платформой» после обновления IDE.** Проект остался на старой версии
платформы: поднять версию проекта или пересоздать его по процедуре вендора.

**Пропала панель.** Интерфейс Eclipse: «Окно → Показать панель» и «Окно → Открыть перспективу».
Панель ошибок здесь же — она показывает не только синтаксис, но и нарушения стандартов на лету.

## Проверка перед отправкой

Перед push прогоняется гейт метаданных (`scripts/check_metadata_regression.py`, ставится вместе с
git-хуками): он ловит объекты и права, которые молча пропали из `.mdo`/`.rights` относительно базовой
ветки. Такое случается, когда IDE перезаписала файл из устаревшей модели: git видит обычную правку,
конфликта нет, и потерю замечают недели спустя. Подробности и разбор механизма —
`1c-metadata/references/edt-mcp-known-issues.md`.
