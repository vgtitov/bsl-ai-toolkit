# Лестница тестирования 1С — какой механизм для чего

Приоритет: **всегда самая нижняя ступень, которой достаточно** для проверяемого
утверждения. Выше — только когда нижняя не может дать доказательство.
Каждая ступень = «что проверяет / что НЕ проверяет / что нужно из доступов».

> **Ось этой лестницы — доказать ПОВЕДЕНИЕ** (отчёт формируется, проведение
> отработало), вердикт по артефакту, headless/CI. Чтобы **посмотреть ДАННЫЕ**
> под пользователем (что в регистре, что видит пользователь X, отладка RLS,
> доступ к данным для AI) — это другая ось, см. `references/data-access-verification.md`
> в этом же скилле. Не путать нумерацию: ступени 0–4 здесь — это про поведение,
> не про уровни доступа к данным.

## Ступень 0 — статика (без базы, секунды)
- BSL Language Server (диагностики), детектор «запрос в цикле» (межпроцедурно),
  валидатор целостности СКД, ratchet против легаси (если есть в проекте).
- Проверяет: синтаксис, анти-паттерны, целостность XML. НЕ проверяет: поведение.
- Доступ: только исходники. **Обязательна всегда** (встроена в pre-commit).

## Ступень 1 — платформенный batch DESIGNER (минуты)
- `LoadConfigFromFiles → UpdateDBCfg -Extension → DumpConfigToFiles` +
  round-trip diff; синтакс-контроль — `/CheckConfig` во ВСЕХ контекстах
  компиляции: тонкий/веб/сервер/внешнее соединение/толстый управляемый/
  модули поставки.
- Проверяет: метаданные валидны для платформы, применение прошло, дрейфа
  свойств нет, модули компилируются под каждый контекст. НЕ проверяет:
  исполнение кода на данных.
- Доступ: 1cv8 на сервере + учётка с правами конфигуратора.
- `/CheckConfig` ловит то, чего не видят ни BSL LS, ни статика: несуществующий
  метод/тип, вызов, недоступный в контексте, битую ссылку метаданных. Ложные
  диагностики линтера тоже отсеиваются здесь — вердикт платформы главнее.

## Ступень 2 — batch ENTERPRISE + runner-EPF (минуты) ← «дымовой прогон»
- Внешняя обработка-раннер, запуск `1cv8 ENTERPRISE /Execute runner.epf
  /C"<параметры>"`; раннер programmatically вызывает проверяемое (печать,
  компоновку СКД), пишет результат/ошибку В ФАЙЛ и завершает сеанс.
- Проверяет: серверная логика реально исполняется на реальных данных
  (печатные формы, СКД-отчёты, проведение, API). НЕ проверяет: UI/формы.
- Доступ: как ступень 1. **Это основной уровень для контуров, куда нельзя
  ставить сторонние фреймворки** (клиентские прод-серверы).
- Пока база НЕ опубликована на веб-сервере — единственный способ проверить
  серверный код на реальных данных вообще. Ограничение: под `/N /P`
  пользователя запуска, а объект `HTTPСервисЗапрос` из кода не конструируется —
  HTTP-контракт расширений так не проверить (см. `references/data-access-verification.md`).
- Вердикт ТОЛЬКО по файлу-результату (маркер OK/FAIL + артефакт): вывод в
  консоль/журнал регистрации не считается доказательством.

## Ступень 3 — UI-смоук через веб-клиент (минуты—десятки минут)
- Веб-клиент + агент/человек проходит сценарий в браузере (открыть отчёт,
  нажать печать, увидеть колонку).
- Проверяет: команды видны, формы открываются, вариант отчёта настраивается —
  то, что batch не покажет. Проверка публикации засчитывается только по
  логу веб-сервера со статусом 200 (либо по факту открывшейся формы).
- Откуда берётся веб-клиент:
  - **файловая база — автономный сервер, публикация НЕ нужна**:
    `scripts/onec_verify.py serve --base <каталог> --port 8315`, дальше `http://localhost:8315/`;
  - клиент-серверная база — публикация на веб-сервере (vrd + конфиг веб-сервера).
- Чем управлять браузером — выбор по стеку и по задаче, не дублировать:

| Способ | Когда он лучший | Чего не умеет |
|---|---|---|
| Браузерное расширение агента | живая отладка в СВОЁМ браузере: сессия и доступы уже есть, видно консоль и сеть, скриншот в отчёт | не воспроизводится в CI, привязан к конкретному агенту |
| Playwright / Chrome MCP | повторяемый сценарий, headless, CI, любой AI-агент | сессию/логин надо готовить отдельно (storage state) |
| Управление экраном и приложениями | UI не веб: толстый клиент, Конфигуратор, окна платформы | дороже и медленнее, хрупко к разрешению и локализации |

- ⚠ Модальные окна платформы блокируют автоматизацию так же, как батч-сеанс:
  диалог ждёт человека, а агент видит «зависание». Это чувствительность к
  «Защите от опасных действий» — см. таблицу диагностики ниже.

## Ступень 4 — фреймворки автотестов (часы на настройку; для команд/CI)
Выбор по задаче:
- **Vanessa Automation** (github.com/Pr-Mex/vanessa-automation, BDD/Gherkin,
  сценарные и UI-тесты через платформенный механизм автоматизированного
  тестирования `/TESTMANAGER + /TESTCLIENT`; запуск в CI — vanessa-runner
  на OneScript). Частый выбор — smoke-набор на каждый MR.
- **YAxUnit** (github.com/bia-technologies/yaxunit, расширение .cfe) —
  юнит-тесты серверного кода, плагин EDT, JUnit-отчёты для CI. Лучший выбор
  для модульных тестов общих модулей — конвенции см. `references/unit-test-conventions.md`.
- **Тестер** (github.com/grumagargler/tester) — сценарные тесты кодом 1С;
  альтернатива Vanessa, когда Gherkin не нужен.
- **1С:Сценарное тестирование** (ИТС) — коробка от вендора, если куплен КИП.
- Проверяет: регресс, сквозные сценарии, юниты. Требует: право ставить
  расширение/обработки фреймворка в тест-базу + (для UI) машину с клиентом.

## Как запустить (ступени 1–2)
```
python scripts/onec_verify.py check --base "срв\ERP_Test" --ext МоёРасширение
python scripts/onec_verify.py smoke --base "D:\bases\erp" --scenario scen.bsl --deploy
```
Без `--host` платформа берётся на этой машине, с `--host <алиас ssh>` — на
сервере 1С рядом с кластером (для контуров с высокой сетевой задержкой до базы —
единственный практичный вариант, см. таблицу диагностики). Один и тот же код
работает обоими транспортами. Ступень 0 живёт в pre-commit, отдельного запуска
не требует.

## Быстрый выбор
| Задача | Ступень |
|---|---|
| «код без анти-паттернов, СКД цел» | 0 |
| «расширение применяется, ничего не задето» | 1 |
| «печатная форма/отчёт реально формируется» | 2 |
| «пользователь это увидит и нажмёт» | 3 |
| «регресс на каждый MR / юнит-тесты» | 4 |

## Ограничения доступности (реальные кейсы)
- Клиентский прод-сервер, ставить фреймворки нельзя → потолок: ступени 0–3
  (раннер-EPF в ТЕСТ-базу — допустимо: это данные, не конфигурация).
- Нет публикации/веб-сервера → ступень 3 заменяется толстым/тонким клиентом
  на машине с доступом, либо пропускается с фиксацией «UI не проверен».
- Зрелый CI: ступени 0–2 на каждый коммит, 4 (VA smoke) на MR, регресс — по релизу.

## Диагностика — не гадать, смотреть на конкретный признак

| Симптом | Причина | Что делать |
|---|---|---|
| `smoke`/batch-сеанс не возвращается, `/Out`-лог пустой, файл-результат не появился | «Защита от опасных действий» — модальный диалог ждёт человека, скрипт его не видит | Снять флаг у пользователя ИБ либо маску в `conf.cfg` (`onec_verify.py protection`) |
| Сеанс к УДАЛЁННОЙ клиент-серверной базе не завершается ДОЛГО (может выглядеть как то же зависание) | Первый сеанс строит локальный клиентский кэш конфигурации по медленному каналу — сотни/тысячи вызовов по ~100 мс | Смотреть, растёт ли каталог кэша (`%LOCALAPPDATA%\1C\1cv8`) между проверками — растёт → сеанс ползёт, не висит. Радикальное лекарство — `--host` на сервер рядом с кластером, тогда обращений по медленному каналу нет вовсе |
| DESIGNER на ЭТОЙ машине выходит с `exit code 1`, лог и вывод ПУСТЫ (не текст ошибки) | GUI-приложение не получило нормальный оконный хендл при запуске из скрипта, ИЛИ путь к базе с кириллицей | См. `references/data-access-verification.md` (раздел про локальный деплой расширения) — та же причина ломает любой batch DESIGNER на клиентской машине, не только деплой |
| DESIGNER: «Error locking infobase for configuration» | Другой `1cv8.exe`/Конфигуратор уже держит базу (в т.ч. ваш собственный интерактивный сеанс) | Найти и закрыть процесс перед батч-запуском |
